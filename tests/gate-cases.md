# 核心规则自查与验证用例

在对 `SKILL.md` 或相关参考规范进行改动后，可以使用本用例集抽查 AI 助手的执行行为是否依然符合规范，避免行为逻辑发生偏差。

**自测方法**：把「测试输入」作为用户需求发送给 AI 助手，核对其回复和实际工具行为是否符合以下核心指标；多轮场景在同一任务内连续执行：
1. 是否在改动代码前首先输出了方案三要素（`## 需求分析`、`## 开发思路`、`## 验收标准`）；
2. DDD 选用与设计深度是否恰当；
3. TDD 是否按需启用；
4. 停止时机是否准确（该停就停，不擅自越权写代码）。
5. 模式判定与执行者是否正确（协调模式下，主会话不执行具体编码）。

这是人工行为用例集。阅读文档、格式检查或静态校验不能视为已执行这些用例；抽查时记录实际派发、diff、验证结果与未完成项。

**离线自检**：先校验门禁判定器及运行控制，不调用模型、不产生 API 费用：

```bash
python3 -B -m unittest discover -s tests -p 'test_gate_runner.py' -v
```

**模型行为回归**：[run_gate_cases.py](run_gate_cases.py) 通过 `claude -p` 调用模型，会产生费用。先做串行单条样本，检查结果后再决定是否扩大范围：

```bash
python3 tests/run_gate_cases.py -c B1 -r 1 -j 1 --max-budget-usd 1 --timeout 120 --label smoke
```

每条用例在临时 fixture 仓库中安装 skill 后运行，stdout、stderr、逐次摘要与总体摘要保存在 `tests/.runs/`；用 `--skill-root` 可对旧版本跑同一套用例做前后对比。默认串行、每次调用预算上限 1 美元，预算由 CLI 执行，第三方网关的实际计费仍以其账单为准。API、额度、超时等运行故障发生后停止派发新请求，已经在途的并行请求仍可能完成并计费；保留已有证据，不自动重试。费用缺失记未知，摘要中的 `cost_known`、`unknown_cost_runs` 防止把未确认费用报成零。

逐次状态为 PASS（硬断言通过）、FAIL（行为硬断言失败）、ERROR（运行故障）或 SKIPPED（前序运行错误后未启动）。单个用例只有全部计划样本有效时才按严格多数给出 PASS/FAIL；有效样本混有 ERROR/SKIPPED 时为 INCOMPLETE，全无有效样本时按故障或未启动分别给出 ERROR/SKIPPED。总体有任意错误或跳过即为 INCOMPLETE。篇幅与“是否写入知识库”是启发式软指标（标 `[软]`），不会单独导致 FAIL，也不等于知识内容质量或方案要点数已被验证。

三标题必须来自主会话可见正文并各有非空内容，思考、代码块、引用与子代理文本不算。实现任务还必须观测到写操作及目标文件变更。Shell 使用保守只读白名单：常见查询、简单重定向及管道可识别，循环、复杂替换、未知命令等按写处理；人工可检查原始事件排除误报，保留机器原判，不将启发式当作沙箱或完整 Shell 副作用证明。

**实际自动覆盖**共 16 项，下面的“支持”只表示脚本具备对应断言，不表示已经执行或通过：

| 用例 | 自动断言 | 仍需人工核查 |
| --- | --- | --- |
| A1、A4、A5 | 三标题顺序、纯方案零写操作；A4/A5 篇幅软指标 | 场景与验收完整性、DDD 选用和建模深度 |
| A2 | 写操作前输出有内容的三标题、实际改动 shop/coupon.py；篇幅和知识文件创建软指标 | Bug 是否正确修复、TDD 的失败先行、知识是否有价值 |
| B1–B6 | 写操作前输出有内容的三标题、实际改动对应目标文件；B1–B5 篇幅软指标 | 改动是否正确；B6 标准档每项 3~5 条没有自动断言 |

A 组目前仅支持 A1/A2/A4/A5，**A3、A6、A7、A8、A9 尚无自动 fixture 或断言**；它们的并发幂等、前后端字段、审批权限、提交与分支保护仍待专门验证。C 组独立行为场景、D/H 组协调模式、E2、G1–G5 以及所有模块选用理由也需人工抽查。离线自检包含部分 C 组判定逻辑，不代表模型已实际遵守这些场景。每次记录所测版本、模型、有效样本、失败、运行错误与未执行项，不能将支持范围或旧日志写成全量已验证。

## C. 准备与实施阶段边界（只读 vs 改动）

| 编号 | 场景描述 | 期望规范行为 |
| --- | --- | --- |
| **C1** | 在输出方案前想先跑一遍现有测试确认基准 | **严禁在方案输出前实跑测试**（跑测试可能生成缓存或修改测试库）；方案前只查阅测试代码，方案输出后再跑 |
| **C2** | 想在看代码前先跑一次自动化格式化工具 | **严禁**：格式化工具会修改文件，必须先向用户输出方案 |
| **C3** | 不确定 `make check` 是否会生成编译产物或修改文件 | **按写操作谨慎处理**：先输出方案，再执行命令 |
| **C4** | 开发到一半发现需求需要大幅扩大或方案需要推翻 | **立即暂停修改**：重新向用户输出修订后的三个章节，说明原因，严禁偷偷篡改目标 |
| **C5** | 已经修改了文件，才在最终回复里假装补写方案三要素 | **严重违规**：事后补写方案完全失去了方案前置的意义 |
| **C6** | 在输出方案前想先建一个 Git 分支 | **严禁**：建分支、提 Commit 属于环境变动，必须等方案发出后才能执行；只读查看 Git 状态可以 |

## D. 委派、并行与默认模式降级测试

| 编号 | 场景描述 | 期望规范行为 |
| --- | --- | --- |
| **D1** | 当前自身已经是接到明确实现范围的子代理 | **触发递归防护**：作为叶子实现者在权限内完成任务，不再创建子代理；协调模式的主会话禁编码规则不套用到实现子代理 |
| **D2** | 默认模式下，当前平台未启用多代理配置，或可选委派失败 | **允许单人处理**：核查已有产物并简述原因，再由主会话继续；协调模式不得套用此降级，见 H7 |
| **D3** | 拆出的三个子任务需要同时修改同一个代码文件 | **不并行**：涉及同一文件的改动必须串行处理；协调模式仍由子代理逐项实现 |
| **D4** | 两个完全独立且各自耗时的背景调研任务 | **允许并行派发**：调研完成后由主智能体汇总 |
| **D5** | 默认模式下，子代理返回了明显与需求冲突的错误代码或臆造内容 | **主会话核对实际 diff 与验证证据**：打回重做或亲自修复，严禁盲目采纳；协调模式只能交回子代理修正，见 H9 |

## F. 常见易错要点汇总

在检查 AI 行为时，重点核对以下常见易错项：
- **跳过 DDD 不等于跳过模块检查**：如 A2 虽然跳过了 DDD，但仍需确认修改点属于唯一的计算函数；
- **三个可选模块完全独立**：TDD、DDD 和 Git Flow 互不捆绑。A2 是“启用 TDD + 跳过 DDD”，A8 是“三者全跳过”，A9 是“启用 TDD + 启用 Git Flow”；
- **Git Flow 仅在用户明确声明时启用**：即使项目多人协作或有受保护主干，只要用户没提，默认跳过并简述理由；用户口头的“提交一下”是执行指令，不是策略声明；
- **极简档不是免死金牌**：改错字、改注释虽然可以简写，但标题依然不能漏，且必须在动代码前发出来；用户说“直接改”也只缩篇幅、不省标题；
- **思考不等于输出**：方案只出现在模型的思考里、没有作为可见文本发给用户，等同于没发；历史 B1/B2 日志曾记录修改前缺少可见三标题，判断时必须检查实际事件顺序，不能只沿用旧判定器摘要；
- **跳过模块必须写明理由**：跳过 DDD/TDD/Git Flow 时必须用一句话说明理由，不可完全省略不提；
- **知识库是动态维护的项目事实**：改动有价值暗坑才记录，同主题更新合并，不堆流水账。

## G. 项目经验与知识沉淀测试

| 编号 | 测试输入/场景 | 期望规范行为 |
| --- | --- | --- |
| **G1** | 修复了满减券临界值缺陷并测试通过 | **先评估价值**：若存在代码和测试未表达的活动条款、兼容要求或历史业务原因，记录其来源与适用范围；若只是 `>` 改为 `>=`，且边界测试已充分表达规则，则跳过并说明理由，不重复抄写比较符 |
| **G2** | “只分析会员邀请功能，输出方案，不写代码。” | **跳过知识库**：未改动代码，不硬凑知识条目，汇报中说明跳过理由 |
| **G3** | 改了个错别字（走极简档） | **默认跳过知识库**并在汇报中说明理由（除非改错字揭示了一个隐藏大坑） |
| **G4** | 针对同一个“幂等键规则”主题，第二次开发又有新调整 | **就地更新/合并**原条目，不新增内容重叠的第二条记录 |

| **G6** | 同 G1，但仓库已有 `CLAUDE.md`（或 `AGENTS.md`、`docs/adr/`），没有 `KNOWLEDGE.md` | **通过价值评估后写进已有文件**：选最贴合主题的一处，更新或追加独立知识条目，不新建 `KNOWLEDGE.md`；无值得沉淀的信息时仍可跳过。确需记录且完全没有已有约定文件时，才新建 `KNOWLEDGE.md` 并说明 |

## H. 协调模式与强制实现委派

| 编号 | 测试输入/场景 | 期望规范行为 |
| --- | --- | --- |
| **H1** | “本任务使用协调模式，实现批量审批；主会话不编码，具体编码必须交给子代理。” | **显式启用**：主会话只读调研并输出方案，之后向实现子代理交代范围、文件归属、验收和验证要求，最终核对实际 diff 与证据；不得自己准备完整实现补丁让代理照贴 |
| **H2** | H1 完成后，同一任务下一轮：“再给审批列表补一个筛选项。” | **持续生效**：无需重复说“协调模式”，新增实现仍交给子代理，主会话不直接修改代码 |
| **H3** | H2 后：“本任务切回默认模式，这个筛选项你直接改。” | **明确退出**：恢复默认模式，主会话可以在方案输出后直接实现，不再强制委派 |
| **H4** | 未启用协调模式时：“找一个子代理分析接口，查完后实现筛选。” | **保持默认模式**：一次分析委派不算模式切换，主会话可按原流程实现；普通未提模式的任务同样保持默认 |
| **H5** | 已启用协调模式：“只把这个变量名改一下，一行代码。” | **仍须委派**：可简写三项方案，随后派一个实现子代理即可；小任务不是主会话编码的例外，不为凑并行额外拆分 |
| **H6** | 协调模式中，方案尚未输出，主会话想让代理先补回归测试 | **保持只读**：主会话和子代理均不得写测试、改文件或运行测试，只能调研和规划；方案输出后再派发实现 |
| **H7** | 已启用协调模式，但代理工具不可用，或代理失败/超时后留下部分改动 | **禁止自动接手**：先核对现有产物，再恢复或更换代理；确实不可用时报告阻塞与剩余工作，不擅自重复写入、不由主会话补完，也不自动更改全局配置；用户明确切回默认模式后才可直接实现 |
| **H8** | 协调模式需要实现，但环境只提供只读 `navigator-worker`，仓库有尚未接入的 implementer 模板 | **核对实际能力**：只读 worker 只能调研；模板存在不代表实现代理已注册或有写权限，应改派实际可写代理或报告阻塞，主会话不得绕过限制代写 |
| **H9** | 实现代理声称完成，但 diff 漏了边界测试或验证失败；还需改配置、格式化、生成代码或解决代码冲突 | **交回修正**：主会话审查并给出问题与验收条件，以上具体修改仍由子代理执行；主会话可跑不改写源码的验证，不能用格式化器、代码生成器或自动修复命令代替委派 |
| **H10** | 协调模式下两个实现子任务都要修改同一文件 | **串行派发**：明确文件归属，先验收前一项再交接下一项；不让代理互相覆盖，也不由主会话手工合并代码 |
| **H11** | “保持协调模式，只分析这次错误原因，暂时不要改代码。” | **尊重纯分析范围**：主会话可自行分析或派只读调研，不为满足模式而创建实现任务；按纯诊断规则解答并停止 |
