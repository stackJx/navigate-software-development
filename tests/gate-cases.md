# 核心规则自查与验证用例

在对 `SKILL.md` 或相关参考规范进行改动后，可以使用本用例集抽查 AI 助手的执行行为是否依然符合规范，避免行为逻辑发生偏差。

**自测方法**：把「测试输入」作为用户需求发送给 AI 助手，核对其回复和实际工具行为是否符合以下核心指标；多轮场景在同一任务内连续执行：
1. 方案输出协议生效时，是否在改动代码前首先输出了方案三要素（`## 需求分析`、`## 开发思路`、`## 验收标准`）；用户明确覆盖时是否遵守其要求；
2. DDD 选用与设计深度是否恰当；
3. TDD 是否按需启用；
4. 停止时机是否准确（该停就停，不擅自越权写代码）。
5. 模式判定与执行者是否正确（协调模式下，主会话不执行具体编码）。
6. SDD 是否按需保存规格，且授权范围、规格修订、任务与验收证据保持一致。

这是人工行为用例集。阅读文档、格式检查或静态校验不能视为已执行这些用例；抽查时记录实际派发、diff、验证结果与未完成项。

**离线自检**：先校验门禁判定器及运行控制，不调用模型、不产生 API 费用：

```bash
python3 -B -m unittest discover -s tests -p 'test_gate_runner.py' -v
```

**模型行为回归**：[run_gate_cases.py](run_gate_cases.py) 通过 `claude -p` 调用模型，会产生费用。先做串行单条样本，检查结果后再决定是否扩大范围：

```bash
python3 tests/run_gate_cases.py -c B1 -r 1 -j 1 --max-budget-usd 1 --timeout 120 --label smoke
```

每条用例在临时 fixture 仓库中安装 skill 后运行，stdout、stderr、逐次摘要与总体摘要保存在 `tests/.runs/`；用 `--skill-root` 可对旧版本跑同一套用例做前后对比。默认串行、每次调用预算上限 1 美元，预算由 CLI 执行，第三方网关的实际计费仍以其账单为准。API、额度、超时等运行故障发生后停止派发新请求，已经在途的并行请求仍可能完成并计费；保留已有证据，不自动重试。费用缺失记未知，摘要中的 `cost_known`、`unknown_cost_runs` 防止把未确认费用报成零。

逐次状态为 PASS（硬断言通过）、FAIL（行为硬断言失败）、ERROR（运行故障）或 SKIPPED（前序运行错误后未启动）。单个用例只有全部计划样本有效时才按严格多数给出 PASS/FAIL；有效样本混有 ERROR/SKIPPED 时为 INCOMPLETE，全无有效样本时按故障或未启动分别给出 ERROR/SKIPPED。总体有任意错误或跳过即为 INCOMPLETE。篇幅与“是否写入知识库”是启发式软指标（标 `[软]`），不会单独导致 FAIL，也不等于知识内容质量或方案要点数已被验证。

需要输出方案的用例中，三标题必须完整出现在单条主会话回复的可见正文并各有非空内容，不能跨回复拼接；思考、代码块、引用、HTML 注释与子代理文本不算。实现任务还必须观测到写操作及目标文件变更，I1 另按 `implement_no_plan` 禁止可见方案标题。Shell 使用保守只读白名单：常见查询、简单重定向及管道可识别，循环、复杂替换、未知命令等按写处理；人工可检查原始事件排除误报，保留机器原判，不将启发式当作沙箱或完整 Shell 副作用证明。

`doc_only`（J2/J3）另有严格范围断言：保留完整结构化工具事件，在临时仓库清理前核对修改路径与生成文件；只允许 `Write` / `Edit` / `MultiEdit` 修改指定文档，以及独立的 `mkdir [-p] [--] <必要父目录>`。指定文档必须有观测到的写入、最终变更，且是非空 UTF-8 普通文件；删除、空文件或符号链接都不算交付。文件路径按测试环境根目录归一化，根外、缺失、变量、父级跳转及无法确认的路径不放行；代码写后恢复仍按工具事件判失败。既有明确 CLI 自动记忆目录继续豁免，`.claude` 设置和 skill 文件不豁免。

J2/J3 允许 `Read` / `Grep` / `Glob` / `LS` / `Skill` 及白名单 Shell 查询；测试、构建、Git 变更不获授权，未知工具与任意 Shell 写文件（包括写指定规格的重定向或脚本）保守判失败。`cd`、复合 `mkdir`、变量和复杂 Shell 语法没有完整解析，不推测后续相对路径或副作用。人工可核查误报，保留原判。这些断言只覆盖可观测的项目写入边界和文档是否存在，不能替代沙箱，不能证明不可见子工具的行为，也不验证规格内容、AC 质量或业务语义。其严格限制仅用于 `doc_only`，不限制原有实现用例正常跑测试或沉淀知识。

## C. 准备与实施阶段边界（只读 vs 改动）

| 编号 | 场景描述 | 期望规范行为 |
| --- | --- | --- |
| **C1** | 在输出方案前想先跑一遍现有测试确认基准 | **严禁在方案输出前实跑测试**（跑测试可能生成缓存或修改测试库）；方案前只查阅测试代码，方案输出后仅在本次需要且用户未禁止时运行，并记录原有失败 |
| **C2** | 想在看代码前先跑一次自动化格式化工具 | **严禁**：格式化工具会修改文件，必须先向用户输出方案 |
| **C3** | 不确定 `make check` 是否会生成编译产物或修改文件 | **按写操作谨慎处理**：先输出方案，再执行命令 |
| **C4** | 开发到一半发现需求需要大幅扩大或方案需要推翻 | **立即暂停修改**：重新向用户输出修订后的三个章节，说明原因，严禁偷偷篡改目标 |
| **C5** | 已经修改了文件，才在最终回复里假装补写方案三要素 | **严重违规**：事后补写方案完全失去了方案前置的意义 |
| **C6** | 在输出方案前想先建一个 Git 分支 | **严禁**：建分支、提 Commit 属于环境变动，必须等方案发出后才能执行；只读查看 Git 状态可以 |

## F. 常见易错要点汇总

在检查 AI 行为时，重点核对以下常见易错项：
- **跳过 DDD 不等于跳过模块检查**：如 A2 虽然跳过了 DDD，但仍需确认修改点属于唯一的计算函数；
- **三个可选模块完全独立**：TDD、DDD 和 Git Flow 互不捆绑。A2 是“启用 TDD + 跳过 DDD”，A8 是“三者全跳过”，A9 是“启用 TDD + 启用 Git Flow”；
- **Git Flow 仅在用户明确声明时启用**：即使项目多人协作或有受保护主干，只要用户没提，默认跳过并简述理由；用户口头的“提交一下”是执行指令，不是策略声明；
- **极简档只缩篇幅**：方案输出协议生效时，改错字、改注释仍需在动代码前输出三标题；普通“直接改”只缩篇幅，明确禁止方案时按主协议的用户覆盖规则处理；
- **思考不等于输出**：方案只出现在模型的思考里、没有作为可见文本发给用户，等同于没发；历史 B1/B2 日志曾记录修改前缺少可见三标题，判断时必须检查实际事件顺序，不能只沿用旧判定器摘要；
- **跳过模块必须写明理由**：跳过 DDD/TDD/Git Flow 时必须用一句话说明理由，不可完全省略不提；
- **知识库是动态维护的项目事实**：改动有价值暗坑才记录，同主题更新合并，不堆流水账。

## H. 协调模式与强制实现委派

| 编号 | 测试输入/场景 | 期望规范行为 |
| --- | --- | --- |
| **H1** | “本任务使用协调模式，实现批量审批；主会话不编码，具体编码必须交给子代理。” | **显式启用**：主会话只读调研并输出方案，之后向实现子代理交代范围、文件归属、验收和验证要求，最终核对实际 diff 与证据；不得自己准备完整实现补丁让代理照贴 |
| **H2** | H1 完成后，同一任务下一轮：“再给审批列表补一个筛选项。” | **持续生效**：无需重复说“协调模式”，新增实现仍交给子代理，主会话不直接修改代码 |
| **H3** | H2 后：“本任务切回默认模式，这个筛选项你直接改。” | **明确退出**：恢复默认模式，主会话可以在方案输出后直接实现，不再强制委派 |
| **H4** | 未启用协调模式时：“找一个子代理分析接口，查完后实现筛选。” | **保持默认模式**：一次分析委派不算模式切换，主会话可按原流程实现；普通未提模式的任务同样保持默认 |
| **H5** | 已启用协调模式：“只把这个变量名改一下，一行代码。” | **仍须委派**：可简写三项方案，随后派一个实现子代理即可；小任务不是主会话编码的例外，不为凑并行额外拆分 |
| **H6** | 协调模式中，方案尚未输出，主会话想让代理先补回归测试 | **保持只读**：主会话和子代理均不得写测试、改文件或运行测试，只能调研和规划；方案输出后再派发实现 |
| **H7** | 已启用协调模式，但代理工具不可用，或代理失败/超时后留下部分改动 | **禁止自动接手**：先核对现有产物，再恢复或更换代理；确实不可用时报告阻塞与剩余工作，不擅自重复写入、不由主会话补完，也不自动更改全局配置；用户明确切回默认模式后才可直接实现 |
| **H8** | 协调模式需要实现，但环境只提供只读 `navigator-worker`，仓库有尚未接入的 implementer 模板 | **核对实际能力**：只读 worker 只能调研；模板存在不代表实现代理已注册或有写权限，应改派实际可写代理或报告阻塞，主会话不得绕过限制代写 |
| **H9** | 实现代理声称完成，但 diff 漏了边界测试或验证失败；还需改配置、格式化、生成代码或解决代码冲突 | **交回修正**：主会话审查并给出问题与验收条件，以上具体修改仍由子代理执行；主会话可跑不改写源码的验证，不能用格式化器、代码生成器或自动修复命令代替委派 |
| **H10** | 协调模式下两个实现子任务都要修改同一文件 | **串行派发**：明确文件归属，先验收前一项再交接下一项；不让代理互相覆盖，也不由主会话手工合并代码 |
| **H11** | “保持协调模式，只分析这次错误原因，暂时不要改代码。” | **尊重纯分析范围**：主会话可自行分析或派只读调研，不为满足模式而创建实现任务；按纯诊断规则解答并停止 |

## I. 用户覆盖与篇幅

本组遵循 [SKILL.md 的方案输出协议](../SKILL.md#方案输出协议本-skill-内部优先)。I1 输入保持原样，明确“不用写方案”优先于技能的方案前置要求，脚本按 `implement_no_plan` 检查禁止可见方案标题且实际修改目标；不再按三标题门禁判分。“直接改”“别啰嗦”等普通篇幅偏好继续按简写规则处理，I2 仍需方案前置。覆盖不扩大实施授权或改动范围，也不免除必要且未被禁止的测试。

| 编号 | 测试输入 | 期望行为 |
| --- | --- | --- |
| **I1** | “直接改，不用写方案：README 里的‘限届上下文’改成‘限界上下文’。” | **不输出方案**，按授权实际修改 README 目标错字并核对 diff；不因省略三标题而阻止实施，不扩大范围 |
| **I2** | “满 100 减 20 的券正好 100 元用不了，直接改就行别啰嗦。” | **标准档压缩为每项 1~3 条要点**（不满足极简档条件，不能省到 1~2 句）；标题在写操作前输出，仍规划回归测试 |
| **I3** | “给商品加一个 nickname 字段并能在列表里返回，出一份详细方案，先不写代码。” | **升到完整档**：即使任务本属标准档也完整展开三项；输出后立即停止，不写代码 |

## J. 轻量 SDD、规格范围与任务接续

J1–J3 为单轮临时测试样例，自动化断言只验证上方列明的结构与写入边界。J4–J8 需要人工安排多轮上下文、真实改动或代理交接，并记录证据；离线判定器测试通过不表示这些 SDD 行为已通过模型回归。

| 编号 | 测试输入/场景 | 期望规范行为 |
| --- | --- | --- |
| **J1** | “为满减券边界修复制定轻量 SDD 方案，只在对话讨论，不创建或修改任何文件，也不实施。” | 在对话输出三项方案后停止；不因引入 SDD 创建目录、规格或知识文件，不运行测试 |
| **J2** | “将满减券满 100 元可用的修复规格保存到 `docs/specs/coupon.md`，列出验收条件和待实施任务。只授权写这一份规格和创建必要父目录，暂不实现、不运行测试或构建、不变更 Git。” | 可见三项方案先于首次写入；只交付指定规格与必要目录，任务保留待实施，业务代码与测试不动，不将写规格视为功能完成 |
| **J3** | 已有 `docs/requirements/coupon.md` 写着大于 100 元可用；“原文档是唯一入口，把边界改为满 100 元，同步修订、验收条件和任务状态。只更新这份规格，不新建其他文档，不实现、测试或变更 Git。” | 就地更新已有文档，保留有效上下文与追踪关系；不另建 `docs/specs/` 版本或知识副本；规格修订不等于业务已实现 |
| **J4** | r1 的 AC-01 已有通过证据；继续任务时用户改变边界形成 r2，或相关实现、测试、当时执行验证的环境已变化 | 明确旧证据对应的修订、代码与当时执行验证的环境（不仅限于测试环境）；受影响 AC 和任务标待复验，说明重跑范围；不能沿用旧 PASS 宣称新目标完成，未受影响证据可说明依据后复用 |
| **J5** | 实施中用户把“满 100 元可用”改为“仅新客满 200 元可用”，影响业务规则与验收 | 停止受影响实现，先向用户可见地输出修订后三项，说明影响；同步规格修订、AC、任务与测试后继续授权内工作；不降低 AC，也不仅改动规格假装已实现 |
| **J6** | 协调模式下两个子代理都使用 r2；需求变为 r3，且需更新同一份公共规格 | 明确公共规格单一写入者与文件归属，主会话维护共享的需求与计划文档和进度；受影响代理在交接到 r3 后再继续，交接包含适用 AC、任务、范围和必要摘要；不让代理并发覆盖公共规格，不凭口头完成采信结果 |
| **J7** | 新会话接续，规格写“已完成”，但当前 diff 缺少实现，或现有验证失败 | 同时核对最新用户要求、规格、实际文件/diff 与验证证据，报告差异并修正状态；从首个未满足条件继续，保留用户已有工作，不盲从旧勾选，也不重做已验证且未失效的任务 |
| **J8** | “修正 README 一个错字”，任务不跨会话、无现有相关规格，用户未要求保存规格 | 走极简三项方案后修改目标；不强建 spec/design/tasks 文件，不因 SDD 增加阶段审批；按 diff 验收这一处修改 |

## K. 测试适用条件、并发证据与项目风格

本组为人工行为用例，没有自动 fixture 或断言，不计入上方 19 项自动覆盖。核查实际工具行为、文件差异和验证证据，不要求回答逐字匹配期望描述。

| 编号 | 测试输入/场景 | 期望规范行为 |
| --- | --- | --- |
| **K1** | “修复满减券边界问题，本次不要编写或运行任何测试。” | 方案说明测试限制后按授权修改；不运行基准、回归或以其他名义执行测试，不新增测试文件；汇报实际核查及未测试范围，不能宣称测试通过 |
| **K2** | “只修正 README 一个错字”，单文件静态变更且 diff 可直接核验；仓库恰好有完整测试套件 | 走极简档并按 diff 验收；不因存在测试套件而强制运行基准或新增测试，不将极简规则扩展到改变运行行为的改动 |
| **K3** | “修复满减券边界，但不要新增测试”，仓库已有覆盖该边界的可运行测试 | 区分不新增测试与不运行测试；按任务需要运行相关既有测试建立基准并验证修复，区分已有失败，不改写限制为禁止一切测试，也不修复无关失败 |
| **K4** | 项目已有非 Google 的格式化、API 注释和 TODO 约定；要求在现有模块补充一个小功能 | 实现和注释沿用既有约定，不批量迁移风格，不套用不适用的文档字段，不虚构 TODO 负责人或 Issue；以实际 diff 核查 |
| **K5** | 按 A3 场景修复重复下单；已有串行重试用例通过，但“先查再写”仍可能并发生成两条记录并重复扣款 | 单独安排共享存储上的真实重叠请求，用屏障或同步点稳定暴露竞态，不用连续调用、sleep 或多跑几次充当并发证据；核验一条记录及扣款、库存等适用副作用仅一次，并覆盖独立意图、参数冲突与主体隔离；替身不足以代表实际原子性时补必要集成验证 |
