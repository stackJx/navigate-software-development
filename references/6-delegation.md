# 子智能体委派模块

本模块是**执行层的可选优化，不是额外的方法阶段**。门禁逻辑、三个开发前必选章节与跨阶段追踪一律不变；默认 solo（主智能体自己串行完成），只在委派门禁全部命中时才 fan-out。

标准工作流是三拍：

```text
① 主智能体先分析具体情况、切出子任务边界
        ↓
② 并行委派子智能体执行
        ↓
③ 主智能体逐个验收、扇入合并结果
```

> 这里的「智能体并行」指用多个子代理同时干活，与开发思路里「同层模块/代码切片可并行」是两码事，勿混淆。

## 1. 委派门禁（何时 fan-out）

满足**全部**条件才委派：

- 当前阶段能切出多个边界清晰、无共享状态、可自包含描述的子任务；
- 并行收益明显大于扇入合并成本；
- 子任务产物能各自独立收敛，不需要彼此的中间结果。

简单任务、小修复、强耦合、需要全局共享上下文、或实现类会互相争用同一契约/迁移时**不委派**——允许结论就是「不委派、主智能体串行完成」（对齐「设计模式由变化点驱动，允许不使用模式」）。

判据是**边界质量**，不是子任务个数。若切出的子任务彼此需要来回对齐，即使数量再多也不该并行；若只有两个但完全独立且都耗时，并行同样成立。委派与否按复杂度缩放，简单 CRUD 不 spawn，如同简单任务跳过 DDD。

## 2. 平台能力映射

方法骨架跨平台一致，调用方式不同。先确认当前运行平台，再选对应实现；无法确认平台或工具不可用时直接 solo。

| 平台 | 启用条件 | 调用工具 | 工作单元定义 |
| --- | --- | --- | --- |
| Codex | `~/.codex/config.toml` 中 `[features] multi_agent = true` | `spawn_agent` / `wait_agent` / `close_agent` | `~/.codex/agents/` 或项目 `.codex/agents/` 下的 `agent_type` |
| Claude Code | 默认可用 | `Agent`（可配 `run_in_background`、`isolation: "worktree"`） | `~/.claude/agents/*.md` 或项目 `.claude/agents/*.md` 的 `subagent_type` |
| 其他/未知 | —— | 无 | solo |

### Codex 调用要点

`spawn_agent({ task_name, fork_turns: "none", message })` —— `fork_turns: "none"` 表示全新隔离上下文，故 `message` 必须**自包含**（子代理不继承会话历史，需带齐路径、范围、约束与期望产出格式）；`wait_agent({ timeout_ms })` 收集结果；`close_agent({ target })` 释放槽位。可复用随附模板 [../agents/navigator-worker.toml](../agents/navigator-worker.toml)（复制到 `~/.codex/agents/` 或项目 `.codex/agents/` 后按 `agent_type` 引用）。

### Claude Code 调用要点

`Agent` 工具的 `prompt` 同样不继承主会话历史，自包含要求一致。并行委派应在**同一条消息内发出多个 `Agent` 调用**才能真正并发。分析类默认用只读检索型 agent；实现类若可能同时改文件，用 `isolation: "worktree"` 隔离，或改为串行。

## 3. 检测与降级（fan-out 前必查）

依次检查，任一不满足即降级为 solo：

1. **递归守卫**：当前若已在子代理内执行，不再递归 spawn，直接 solo；
2. **能力可用**：平台委派能力未开启或对应工具不可用 → solo；
3. **运行时失败**：spawn 返回失败、工作单元类型不可用或子代理无法启动 → 停止继续 spawn，改 solo，不把部分结果当完整结论。

无论委派还是降级，都在答复中一句话说明**实际执行方式与原因**（如「已并行委派 4 个需求角色梳理」或「multi_agent 未开启，降级 solo」）。本 Skill 在无委派能力的环境下默认走 solo，开箱即用。

## 4. 各阶段拆分建议

| 阶段 | 可并行 fan-out | 必须由主智能体集中/串行 |
| --- | --- | --- |
| ① 需求分析 | 按角色/用例并行梳理 | 合并术语表、缝合跨角色交接链、消歧 |
| ② DDD | 每聚合/每上下文的局部战术设计 | 统一语言、Context Map、跨边界一致性矩阵 |
| ③ 开发思路 | **依赖图建立后**按同层模块/纵向切片 | 依赖图构建；避免并行切片争用同一契约或迁移 |
| ④ TDD | 独立切片/不同测试层并行 | 先建绿灯基线；外向内推进（暂停外层→窄测试→回外层）串行不可拆；证据汇总 |
| ⑤ 实现验证 | 独立切片并行编码（同③约束） | 扩大验证收敛 |

约定：**分析/建模/审查类可并行；实现类默认串行**，避免文件冲突。

## 5. 验收与扇入

**验收（不可跳过）**：主智能体先**逐个验收**子代理产出——核对是否符合需求/验收标准、证据是否充分、有无臆造、越界或彼此冲突；不合格的**打回重派或自行补做**，绝不盲目采纳。子代理并行只加速产出，正确性由主智能体负责。

**扇入合并（reconverge）**：验收通过后并回 `## 跨阶段追踪` 的单一链条与三个开发前必选章节；子产物视同「上游产物」，不留多份平行产物、不臆造规则；阻塞性业务决策仍由主智能体显式提给用户，不替用户拍板。

## 资料基础

预检降级与并行 fan-out 范式，借鉴 Codex 生态中 story-review 与 maestro-flow 的实践。
