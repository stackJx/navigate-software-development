# 子代理委派与协调模式指南

默认模式下，委派是可选的执行优化；用户明确启用协调模式后，所有具体实现必须委派。模式选择与持续范围见 [SKILL.md](../SKILL.md#执行模式与子代理)。两种模式均按主协议处理方案输出与明确的用户覆盖，委派不会放宽范围、权限或验收要求。

## 1. 职责分工与只读底线

| 工作 | 默认模式 | 协调模式 |
| --- | --- | --- |
| 只读调研、需求设计、拆分任务 | 主会话完成，可按需委派 | 主会话负责，可委派调研 |
| 生产代码、测试、脚本、配置及格式化 | 主会话或实现子代理执行 | 仅实现子代理执行，包括极小改动 |
| 返工修补、冲突解决中的代码编辑 | 主会话或实现子代理执行 | 交回原子代理或重派 |
| 审查、验收和最终汇报 | 主会话负责 | 主会话负责 |

协调模式的主会话可以编写非实现的分析与文档说明，提出设计约束、接口约定和评审意见，但不得编写完整实现或补丁，再让子代理照贴。说明文档若包含可执行脚本、实际配置或其他具体实现内容，仍应交给实现子代理。模式是任务分工，不是全局只读设置，不自动修改用户配置。

采用 SDD 时，共享的需求与计划等规格文档由主会话维护；在协调模式下，若文档包含可执行脚本、实际配置或完整实现，仍属于实现子代理的职责。只读方案任务仍不写文件，保存规格文档须在授权范围内，并按 [方案输出协议](../SKILL.md#方案输出协议本-skill-内部优先) 处理默认前置方案与用户明确覆盖。规格文档只是协作依据，不会自动启用协调模式；具体实现仍遵守当前执行模式分工。规格文档保存规则见 [SDD 指南](9-spec-driven-development.md)。

**默认在方案输出前，主会话和子代理均只读**，只能检查代码、既有测试和 CI 结果；不能提前写复现测试、运行会产生文件的测试或修改环境。主会话按 [方案输出协议](../SKILL.md#方案输出协议本-skill-内部优先) 确定派发前的方案输出状态：已向用户输出三项，或用户明确禁止输出方案/撤销本流程且有直接用户指令依据。明确覆盖只改变方案输出要求，不扩大实施授权，也不自动切换执行模式。实现子代理收到上述状态、用户实施授权依据及完整任务摘要后，不必重复对用户发方案；没有已发送方案且缺少明确用户覆盖依据、任务摘要缺少关键内容、范围发生重大变化或关键决策未定时，应只读核查并向主会话报告，等待补齐，不自行决定省略方案。

协调模式下的典型流程：

```text
主会话只读调研、按主协议确定方案输出状态
               ↓
主会话按文件归属派发实现子代理（通常串行）
               ↓
子代理实现并验证 → 主会话检查实际差异与验收证据
               ↓
不合格：交回或重派；合格：主会话统一汇报
```

## 2. 拆分任务与串行、并行的选择

**先决定谁实现，再决定是否并行。** 协调模式下，小 Bug、单文件修改和简单 CRUD 也要委派，通常一个实现子代理串行完成即可。默认模式下，这类任务通常直接完成。

只有边界清晰、互不依赖、不存在共享文件或共享可变状态，且收益明显时，才并行派发。例如分别调研不同外部库，或实现已确定接口约定、文件归属互不重叠的独立模块。

以下工作保持串行：

- 前一任务的结果是后一任务的输入，或共享接口约定尚未确定；
- 需要修改同一文件、共同配置或共享数据库迁移；
- 需要频繁交换中间结果才能继续，或并行管理成本超过收益。

主会话先明确公共接口约定与文件归属；每个子代理只负责分配给它的修改范围。共享工作区内保留已有改动，不覆盖其他任务产物。若使用隔离工作区，按环境能力安排集成；协调模式中的冲突修复仍由实现子代理执行。

共享的规格文档保持单一写入者。子代理回报任务状态、证据与修订建议，由主会话复核后统一更新；不要让并行实现代理共同编辑共享规格，也不由子代理自行修改验收目标。

## 3. 实现任务必须携带的上下文

无论平台是否继承会话历史，派发信息都应明确以下内容，避免子代理自行推断授权和职责：

```text
角色：本次任务的实现子代理；自行实现，不递归创建子代理。
方案输出状态：已向用户输出三项；或用户明确禁止方案/撤销本流程，附直接用户指令及实施授权依据。
实施摘要：无论是否向用户发送方案，均提供任务目标、范围、实施思路、验收条件与验证摘要，以及当前有效的修订。
规格依据（存在时）：规格文档绝对路径、当前修订版本、本任务编号和 AC 编号，以及相关规则与验收内容摘要；不能只发文件路径。
任务范围：项目绝对路径、目标、允许修改的文件/目录、禁止触碰的范围。
依赖与归属：接口约定、前置结果、其他任务的文件归属、需要串行等待的工作。
验证方法：应执行的检查、可用环境及已知限制。
交付要求：实际修改清单、关键决策、逐项对应任务/AC 的验证命令及结果、未完成项与阻塞。
```

“主会话不编码”只约束协调者；实现子代理收到明确任务和可用权限后应自行实施，不能再次委派来规避职责。调研子代理保持只读，不能因继承了整个开发请求而自行开始实现。

子代理发现规格修订、用户要求或实际代码与派发摘要冲突时，立即暂停受影响的所有写入操作（含代码、配置、测试与文档），并附带证据上报，不得自行降低验收条件（AC）或修改公共约定。主会话按变更规则确定当前有效规格，并向受影响代理补发修订说明；其他互不依赖的任务可继续推进。

## 4. 平台能力与模板

| 环境 | 派发前应核实的能力 | 使用边界 |
| --- | --- | --- |
| Codex | 当前实际暴露的子代理创建、通信、等待工具及写权限 | 工具名、可用角色和历史继承方式以当前环境说明为准 |
| Claude Code / Antigravity 等 | 当前会话是否支持子代理、角色选择及工作区隔离 | 不根据平台名称推定功能默认开启 |
| 无可用子代理的环境 | 是否确实缺少创建工具，或子代理仅有只读权限 | 按下节的模式规则处理，不虚构派发成功 |

本项目为两个平台各提供一套职责相同的模板：

| 角色 | Claude Code（`.md`，frontmatter 限定工具） | Codex（`.toml`，sandbox 限定权限） |
| --- | --- | --- |
| 只读调研、设计与审查 | [claude/navigator-worker.md](../agents/claude/navigator-worker.md)，`tools: Read, Grep, Glob` | [codex/navigator-worker.toml](../agents/codex/navigator-worker.toml)，`sandbox_mode = "read-only"` |
| 负责具体实现的子代理（不创建更多子代理） | [claude/navigator-implementer.md](../agents/claude/navigator-implementer.md)，额外开放 `Edit, Write, Bash` | [codex/navigator-implementer.toml](../agents/codex/navigator-implementer.toml)，`sandbox_mode = "workspace-write"` |

接入方式：

- **Claude Code**：把 `agents/claude/*.md` 复制或软链接到项目 `.claude/agents/` 或用户级 `~/.claude/agents/`，用 `/agents` 确认已加载后，按名称（`navigator-worker` / `navigator-implementer`）派发。
- **Codex**：先核对当前平台和版本是否支持自定义代理目录及角色选择。支持时，把 `agents/codex/*.toml` 复制到项目 `.codex/agents/`（项目需被 Codex 信任）或用户级 `~/.codex/agents/`；仅在实际工具提供 `agent_type` 参数时，按文件内的 `name` 字段选择 `navigator_worker` / `navigator_implementer`。不支持该参数或加载机制时，把职责、范围和验收要求传给当前可用的子代理，并核实其实际工具与写权限。

模板文件存在不代表已经注册为可调用角色，也不能提升运行环境实际授予的权限。使用环境已有的合适角色与权限；没有自定义角色加载能力时，可把任务要求传入可用子代理。不要自动修改用户全局配置、将只读模板改成可写，或把只读子代理当作实现代理。

## 5. 失败恢复与降级边界

派发失败、执行中断或结果不完整时，先检查代理状态、实际文件差异与已有验证产物，明确已经完成的部分，再决定恢复原代理还是重派。前一个代理仍在写入时，不向另一个代理分配相同文件；需要接替时先确认原代理停止，避免重复修改。不要无差别反复重试。

恢复执行时同时核对规格修订版本与任务状态；旧证据只证明当时验证的代码、文件、当时执行验证的环境与条件，出现新修改（含代码、配置、测试与文档）、接口或行为约定变动后，需重新核验其适用性。交接摘要写明可复用成果、待复验项和剩余任务，不能依据旧勾选直接宣布完成。

- **默认模式**：环境不支持子代理或委派失败时，可以自动回到主会话串行完成；接手前同样要核对已有产物。
- **协调模式**：优先恢复或重派有实际写权限的实现子代理。若工具不可用、启动或执行失败无法恢复，或现有权限只能只读，报告具体阻塞、已完成产物和未完成部分；不得自动改由主会话实现。只有用户明确切换回默认模式，主会话才可接手编码。
- **自行完成任务**：每个子代理都自行完成分配的任务，不创建更多子代理。实现代理遇到超出范围、权限不足或阻塞性决策，带证据交还主会话，由主会话调整任务或报告阻塞。

告知用户实际状态，例如“已派发一个实现子代理，完成后由主会话验收”或“当前没有可写实现代理，编码尚未开始”；不能把派发、代理自述完成或模板已存在当作实际完成。

## 6. 验收与汇总

1. **核查实际产物**：主会话读取实际 diff/文件和测试证据，检查范围、接口约定、遗漏与验收标准，不仅转述子代理结论。主会话可以运行不主动改写源码的验证；自动修复、格式化、更新测试快照或生成源码等操作交给实现子代理。
2. **处理不合格结果**：给出问题位置、依据和预期行为。协调模式下交回原代理或重派实现，复核修订后的产物；默认模式可以由主会话补充修复。主会话始终对最终质量负责。
3. **统一交付**：对照当前有效方案汇报实际修改、验证结果、经验留存（或知识库更新）和遗留问题，明确未验证项；保存了公共规格文档时，主会话核查证据后统一同步状态。不用零散子日志代替结果，也不在最终汇报时补写或修改验收目标。
