<a id="1-适用性与投入门禁"></a>
## 1. 适用性与复杂度分级

DDD 的真正价值是理清复杂业务逻辑，而不是凭空多写一堆文件和类。
根据当前问题的实际复杂度，**挑选最轻量的合适级别**，千万不要为了追求形式完整而做全套设计：

| 级别 | 适用场景 | 建议做法 | 输出内容（编号见 [§11](#11-建模流程与交付物)） |
| --- | --- | --- | --- |
| **L0 轻量模块化** | 简单的增删改查（CRUD）、数据录入、报表查询、简单校验 | **不做 DDD**，把接口、逻辑和数据库操作分清楚即可 | 不输出 DDD 产出物，在开发思路中简述跳过理由 |
| **L1 局部设计** | 局部逻辑较复杂，涉及特定状态流转、组合计算规则或严格约束 | 仅在对应业务模块内划分实体、值对象和聚合根 | 输出第 5、6、12 项（若涉及事务或防重补第 8 项） |
| **L2 业务语言对齐** | 跨团队对同一术语理解不一致，概念归属产生冲突 | 重点梳理统一语言、业务边界与职责归属 | 输出第 1、2、3、11、12 项 |
| **L3 跨边界协作** | 多个模块互相调用频繁、依赖混乱、需要引入防腐层或分布式一致性 | 在 L2 基础上补充接口契约、防腐层适配、事件通知与长流程控制 | L2 + 第 7、8、10 项 |
| **L4 全面建模** | 公司的核心业务引擎，规则极其复杂、长期持续演进且改错代价巨大 | 进行完整的战略边界划分与深入的战术建模 | 输出全部 1–12 项 |

> [!NOTE]
> 设计级别取决于**当前要解决的问题本质**，而不是整个项目的代码行数：在一个百万行的大系统里修一个边界计算 Bug 通常只是 **L1**；而一个刚起步的小项目如果几个部门对核心概念争吵不休，则属于 **L2**。
> 如果代码只是查数据库展示、跑个脚本或改个小配置，坚决使用最简单的写法，跳过 DDD。

在新建一个业务模块或聚合前，先问自己四个问题：
1. 这是一个全新的业务概念，还是现有业务里的一个普通用例？
2. 这里的复杂是因为业务逻辑本身复杂，还是因为之前的代码写得烂、依赖乱？
3. 这个边界能否用大白话说清楚并独立演进，还是单纯为了让目录显得“高大上”？
4. 拆分之后，改动代码是更容易定位和测试了，还是找个代码要跳五六个文件？

<a id="2-战略设计语言子域与限界上下文"></a>
## 2. 战略设计：统一语言与业务边界

### 2.1 建立统一语言

从业务交流、需求说明、已有代码和测试用例中提炼出核心的名词、动作和状态。确保同一个概念在讨论、文档、测试用例和代码变量名中完全一致。

遇到以下情况时，先停下编码，把语言说清楚：
- **同词异义**：同一个词，业务人员、前端和后端理解完全不同；
- **同义异词**：同一个概念，代码里一会儿叫 `account`，一会儿叫 `user`，一会儿叫 `member`；
- **状态含糊**：状态名看不出允许做什么（如用 `status = 2` 代表“等待财务二次确认”）；
- **用布尔值遮掩状态**：用 `is_valid`、`is_done` 等布尔字段强行拼凑复杂的业务流转；
- **黑话与模糊词**：出现“特殊处理”、“一般情况”等缺乏明确可验证规则的表述。

> [!TIP]
> 统一语言只需在**当前业务模块内**达成一致，不需要整个公司所有系统用同一套模型。跨模块之间如果叫法不同，通过翻译转换即可。

### 2.2 业务分类：核心、支撑与通用

- **核心模块**：产品的核心竞争力所在（比如电商的推荐与计费、交易引擎），需要倾注最主要的精力，精心建模；
- **支撑模块**：业务不可或缺但非独家壁垒（比如内部权限审批、工单流转），保持逻辑清晰、避免过度设计；
- **通用模块**：行业通用的成熟功能（比如发短信、通用用户认证、文件存储），优先采购或复用现成组件，不做定制化复杂设计。

### 2.3 划分业务边界（限界上下文）

业务边界（Bounded Context）是某种业务语言成立的范围。它不一定对应一个微服务或一个独立 Git 仓库，在单体项目里也可以是一个清晰独立的子目录或模块。

寻找边界的实用技巧：
- **概念不同**：比如“商品”，在商品中心关注的是规格、类目、图片；在仓储物流关注的是重量、体积、打包规则；在结算中心关注的是单价、折扣。强行把它们塞进一个万能的 `Product` 大类中，只会让代码越来越臃肿。拆分为不同的模块各自建模，通过商品 ID 关联，往往更简洁。
- **演进速度不同**：经常变动的前台业务，不应与几个月不变的底层核算逻辑强行揉在一起。
- **职责清晰**：每个模块明确自己“管什么事实”、“提供什么能力”，以及最重要的——**“明确不管什么”**。

<a id="3-上下文映射与协作关系"></a>
## 3. 模块间的协作关系与依赖管理

明确模块之间如何交互，谁依赖谁：

- **合作关系（Shared Partnership）**：两个模块由同一个团队维护，互相配合一起调整；
- **上游供应 / 下游消费（Customer-Supplier）**：上游提供基础能力，下游提出诉求，上游排期支持；
- **防腐层（ACL - Anti-Corruption Layer）**：当调用外部第三方系统或历史遗留老系统时，**在入口处加一层适配转换**，把对方糟糕奇怪的数据格式转成本系统清晰的内部对象，绝不让外部脏数据污染内部核心逻辑；
- **公开协议 / 开放接口（Open Host Service）**：上游对外提供稳定、带版本号的公共 API 供多个下游调用；
- **各走各路（Separate Ways）**：如果两个小功能协作成本极高，不如各写各的，接受必要的少量重复代码，避免盲目共享导致强耦合。

**协作红线**：
1. 禁止一个模块直接去读写另一个模块的内部数据库表；
2. 跨模块调用只传递必要的业务数据或稳定 DTO，不要把内部完整实体暴露出去；
3. 共享模块（Common/Utils）只放真正通用的工具（如字符串处理、日期格式化），严禁把具体业务实体塞进公共包，防止成为“垃圾桶”。

<a id="4-四色建模"></a>
## 4. 业务事件建模（四色建模）

如果业务流程较长，不知道怎么拆分类和方法，可以按业务发生的时间线进行梳理：

1. **业务事件/时段（粉色）**：已经发生的客观事实或一段历程（如“订单已创建”、“合同已签约”、“支付完成”）；
2. **参与角色（黄色）**：谁以什么身份参与（如“买家”、“审核员”、“承运商”）；
3. **关键人/物/地点（绿色）**：涉及的具体事物（如“用户”、“车辆”、“货架”）；
4. **规则与模板（蓝色）**：依据的标准或配置（如“退款政策模板”、“会员折扣规格”）。

梳理步骤：
- 先按时间顺序把所有关键**业务事件**排开；
- 搞清楚每个事件由谁发起（角色）、针对什么对象（人或物）、依据什么规则（政策模板）；
- 标明哪些事件是必须在同一瞬间成功的（原子操作），哪些是可以异步稍后处理的。
这样核心实体、值对象和业务状态流转就自然浮出水面，不需要凭空硬憋类图。

<a id="5-战术建模与行为归属"></a>
## 5. 核心战术设计（实体、值对象、聚合根）

### 5.1 实体（Entity）

实体是指**具有唯一标识、并且状态会随时间改变**的业务对象（如“用户”、“订单”）：
- 必须有明确唯一的业务 ID（如 `order_id`）；
- 核心状态改变必须通过有业务含义的方法（如 `order.cancel(reason)`），严禁公开无脑的通用 setter 让外部随心所欲改状态；
- 对象自身负责维护内部属性的基本合法性。

### 5.2 值对象（Value Object）

值对象是指**没有独立 ID、只关心具体数值**的对象（如“金额”、“地址”、“时间区间”、“经纬度”）：
- **不可变**：一旦创建就不能修改属性；如果需要变动，返回一个全新创建的值对象（如 `money.add(otherMoney)`）；
- **自带校验与计算**：把金额单位（分/元）、币种、数值计算等逻辑封装在内部，防止数值单位混乱（比如把分当成元处理）；
- 比较两个值对象时，只要所有属性相等，就认为它们完全相同。

### 5.3 聚合与聚合根（Aggregate & Aggregate Root）

聚合是**一组必须一起保持数据正确性的对象合集**，聚合根就是这组对象的总负责人：
> 核心原则：**哪些数据必须在同一次操作中同时保证正确，它们才属于同一个聚合。**

- **聚合根是唯一的外部修改入口**：外部代码不能直接修改聚合内部的子实体，所有操作必须调用聚合根的方法；
- **聚合尽量做小**：只包含强关联的数据。不要把整张关系网都塞进一个聚合；比如“订单”和“商品”是两个聚合，订单只保存 `product_id`，而不是把整个商品对象塞在订单里；
- **一个实体也可以是一个独立的聚合**：没有级联子对象时，它自己就是聚合根，不需要硬套父子结构；
- 聚合内部代码只做内存中的纯业务计算与状态改变，**严禁在聚合内部调用网络接口、读写文件或发消息**。

### 5.4 领域服务（Domain Service）

当某段核心业务逻辑**不自然属于任何一个具体的实体或值对象**时，才提取为领域服务（如“根据多种优惠券与会员等级计算最优组合折扣”）：
- 纯业务计算，无自身状态；
- 不处理 HTTP 协议转换、不负责直接发 MQ、不处理线程调度；
- 避免把所有逻辑都写在 Service 里（不要退化成贫血模型）。

### 5.5 领域事件（Domain Event）

领域事件表示**业务上已经发生的重要事实**（如 `OrderPaidEvent` 订单已支付）：
- 用完成时命名；
- 事件内容不可修改，记录发生时的核心事实；
- 用于模块内部解耦或通知其他下游模块；
- 区分两类事件：
  - **模块内领域事件**：当前模块内部使用，可包含较丰富业务信息；
  - **跨模块集成事件**：发到消息队列供外部系统订阅，只包含稳定、最少的数据契约（如仅包含 ID），避免内部数据结构泄露。

### 5.6 业务逻辑归属原则

写一段业务逻辑时，优先放到最合适的地方：
1. **单个值对象**能独立完成的（如计算两个金额相加、校验手机号格式） $\rightarrow$ 放在 **Value Object**；
2. **单个实体内部**的状态与规则（如修改用户昵称、重置密码） $\rightarrow$ 放在 **Entity**；
3. **涉及多个内部子实体必须一起变动**的规则（如订单明细金额汇总、状态联动） $\rightarrow$ 放在 **Aggregate Root**；
4. **纯业务逻辑但跨多个聚合**，不适合强塞给任何一个实体的 $\rightarrow$ 放在 **Domain Service**；
5. **从数据库查出数据、调用领域逻辑、保存回数据库、调用外部接口发通知** $\rightarrow$ 放在 **应用层用例（Application Use Case / Service）**。

<a id="6-应用用例与六边形边界"></a>
## 6. 分层架构与依赖边界

清晰的分层不是为了制造目录，而是为了**让核心业务逻辑不受数据库、网络框架等外部技术的绑架**：

```text
用户请求 / 外部触发 (Inbound Adapters: Controller, MQ Consumer)
                      ↓
应用层用例 (Application Use Case: 组织流程、事务管理)
                      ↓
核心领域层 (Domain: 实体、值对象、核心规则)
                      ↑
外部能力实现 (Outbound Adapters: 数据库实现 Repository Impl, 第三方接口调用)
```

- **核心原则：内层不依赖外层**。领域层（Domain）只包含纯粹的业务规则，不引用 Controller、ORM 框架或数据库驱动；
- **接口在内，实现在外**：领域层只定义自己需要什么接口（例如“我需要一个根据订单号查询订单的仓储接口”），由外层 Adapter 去实现具体是通过 MySQL、Redis 还是 RPC 查询；
- **小项目轻装上阵**：小项目不需要拆十几个子模块，在同一个工程里按包路径隔开职责即可，避免空壳工程。

<a id="7-repositoryportadapter-与防腐层"></a>
## 7. 仓储、外部适配与防腐层

### 7.1 仓储（Repository）

- 仓储是面向**聚合根**的存取接口，不是给每张数据库表都建一个；
- 方法名体现业务含义（如 `find_by_user_id`、`save`），而不是通用的底层 SQL 拼装；
- 明确区分“数据不存在”与“系统报错”，不要把各种异常统统吃掉返回 `null`；
- 复杂的列表组合筛选、报表导出等读操作，可以直接用专门的查询服务写 SQL 查询，不需要硬走仓储组装聚合根。

### 7.2 适配器与防腐层（Adapter & ACL）

- 当调用微信支付、短信服务或外部旧系统时，必须封装专门的适配器；
- 在适配器内部把外部系统的状态码、错误信息转换成当前系统容易理解的异常或返回结果；
- 绝不要把外部第三方的原始对象直接透传到核心业务代码里。

<a id="8-事务一致性与长流程"></a>
## 8. 事务、数据一致性与异步流程

### 8.1 本地事务

- **一个用例在一次本地事务中，尽量只修改一个聚合根**；
- 事务内严禁调用耗时的外部网络请求（如发邮件、调第三方支付、发短信），避免长事务锁死数据库；
- 永远不要把“写数据库”和“写 Redis 缓存”误当成是在一个事务里；通常在数据库事务提交成功后再使缓存失效。

### 8.2 跨模块数据一致性与异步消息

如果一个操作需要联动多个模块（例如“支付成功”后需要“扣库存”、“加积分”、“发通知”）：
1. 采用**最终一致性**：核心交易先落库，通过可靠消息队列异步通知下游；
2. **防重复处理（幂等性）**：消费者必须支持重复消费同一个消息而不会造成重复扣款或发货；
3. **不要轻信“消息绝对不丢、绝对不重”**：在网络环境下重试是不可避免的，消费端做好唯一键约束或业务幂等去重是唯一可靠的方案。

### 8.3 长流程处理（Saga / 补偿机制）

对于跨多个系统的长流程操作（如预订机票+酒店）：
- 每一步都设计对应的“反向补偿动作”（例如预订失败时执行“取消预订”）；
- 补偿是执行一个新的业务操作，不是数据库底层的回滚；
- 记录每一步的流转状态，遇到故障无法自动恢复时，提供报警和人工介入界面。

<a id="9-分包命名与架构约束"></a>
## 9. 目录组织与命名建议

目录划分顺应项目既有习惯即可，典型结构参考：

```text
src/
└── modules/
    └── order/                  # 业务模块（订单）
        ├── domain/             # 领域模型：实体、值对象、仓储接口
        ├── application/        # 应用用例：处理流程编排、事务
        ├── infrastructure/     # 基础设施实现：数据库读写、外部 API 客户端
        └── interfaces/         # 对外入口：Web 控制器、MQ 消息监听
```

命名习惯：
- 优先用大白话的业务词汇，不要堆砌毫无意义的缩写；
- 用例（Use Case）用动词+名词命名（如 `CreateOrderUseCase`、`ApproveRefundService`）；
- 事件用过去时命名（如 `OrderCancelledEvent`）。

<a id="10-设计模式选择指南"></a>
## 10. 设计模式选择指南

**先写简单直接的代码，当出现明显的变化或痛点时，再挑选最简单的模式重构。**

| 业务实际情况 | 推荐模式 | 说明与避坑 |
| --- | --- | --- |
| 规则简单直接，基本不会变 | **普通 if-else 或函数** | 不要提前抽象，直接写最直观 |
| 同一个业务决策有多种独立演进的算法/规则 | **策略模式 (Strategy)** | 如不同会员等级的计费策略，确保后续能方便扩展新策略 |
| 实体状态流转复杂，不同状态下允许的行为截然不同 | **状态模式 (State) / 状态机** | 把复杂的状态流转和非法操作校验收敛到状态机里 |
| 多个处理步骤需要按顺序链式执行或过滤 | **责任链 / 管道模式 (Pipeline)** | 如请求参数层层校验，注意链条不要过长导致调试困难 |
| 对象的构建过程极其繁琐、涉及多个校验 | **工厂 / 构建器 (Builder)** | 简单两三个参数的对象直接 `new`，不要写多余的工厂 |
| 业务逻辑需要访问外部系统或老旧系统 | **适配器 / 防腐层 (Adapter / ACL)** | 转换数据格式，阻隔外部污染 |

<a id="11-建模流程与交付物"></a>
## 11. 建模步骤与产出物

在复杂的 L4 任务中，完整的梳理步骤如下（简单任务只需按分级要求做最小部分）：

1. **理清事实**：收集需求、参与角色、核心流程与未知疑问；
2. **统一语言**：提炼关键业务名词与统一术语表；
3. **划定边界**：明确各个业务模块的职责范围与协作方式；
4. **梳理流转**：按时间线梳理核心事件、参与角色与业务动作；
5. **定义模型**：划分实体、值对象、聚合根与领域事件；
6. **确定规则**：明确聚合根维护的必须一致的数据规则；
7. **设计用例**：画出核心业务操作的调用流程；
8. **定义契约**：明确仓储接口与外部适配器规范；
9. **处理异常与一致性**：明确跨模块重试、幂等与补偿方案；
10. **落地实现**：顺应项目目录编写代码，按需选用设计模式。

产出物速查清单（供 [§1 投入分档](#1-适用性与投入门禁) 引用）：
1. 统一术语表；
2. 业务模块划分与定位；
3. 模块协作与依赖图；
4. 业务事件时序梳理；
5. 聚合根与数据约束清单；
6. 核心业务用例执行步骤；
7. 仓储与外部接口定义；
8. 数据一致性、防重（幂等）与重试补偿方案；
9. 目录结构规划；
10. 架构与设计模式决策说明；
11. 需求与用例对照关系；
12. 待确认疑问与决策人。

<a id="12-设计门禁与常见反例"></a>
## 12. 自查清单与常见避坑指南

<a id="121-交付门禁"></a>
### 12.1 交付自查清单

在向用户提交设计前，对照以下关键问题自查：

- [ ] 核心术语是否有统一、清晰的定义，没有同名异义的混淆？
- [ ] 每一条业务规则是否由唯一的一个模块负责维护，没有在各处重复写多套规则？
- [ ] 模块边界划分是否有充分的业务理由，而不是单纯为了把文件拆开？
- [ ] 聚合内部必须同时保持正确的数据规则是否明确，外部有没有越过聚合根随意修改内部状态？
- [ ] 核心业务逻辑是否独立干净，不依赖具体的数据库驱动、网络框架或传输协议？
- [ ] 仓储和外部接口的职责是否清晰，没有变成“万能的大杂烩接口”？
- [ ] 跨模块的异步调用、消息重试和幂等防重机制是否考虑周全？
- [ ] 引入的设计模式是否切实解决了复杂度问题，还是带来了不必要的层层嵌套？
- [ ] 设计方案是否紧密贴合当前项目的既有技术栈与编码规范，没有照搬死板的外来框架？

### 12.2 常见反例与纠正

| 常见反例 | 存在的问题 | 纠正做法 |
| --- | --- | --- |
| **先按数据库表建实体** | 把数据表结构当成了业务模型，导致代码全是增删改查 | 先从业务场景、行为和规则出发设计模型，再决定如何存储到数据库 |
| **所有实体属性都提供 public setter** | 任何调用者都能随意篡改状态，绕过所有业务检查 | 私有化属性，对外提供有业务含义的方法（如 `cancelOrder()`） |
| **把所有关联数据都塞进一个大聚合** | 一次只改一个状态，却锁住了整个庞大的对象图，引发并发冲突 | 聚合尽量做小，只装必须同时保持正确的数据，其余数据只记录 ID |
| **所有业务全写在 Service 里（贫血模型）** | 实体变成了只有字段的空壳，业务逻辑散落在各处无法复用 | 能由实体自身计算和校验的逻辑放进实体，Service 只负责流程编排 |
| **万能仓储暴露通用 CRUD** | 破坏了聚合根的完整性，外部可以随意绕过限制更新子表 | 针对聚合根按实际需要定义精简的存取方法 |
| **在本地数据库事务里调外部网络接口** | 外部接口慢或者超时会导致数据库连接池被占满锁死 | 事务里只改本地数据库，事务提交后再异步调外部接口 |
| **消息发送与数据库提交未做防丢失防重** | 数据库保存了但消息没发出去，或消息重复导致业务重复处理 | 本地消息表或事务消息保障发送，消费端通过业务唯一标识保证幂等 |
| **看到几行分支就强上设计模式** | 徒增类和接口数量，看代码要跳转好几层 | 简单稳定的逻辑直接写代码，有真实可扩展需求时再引入模式 |
| **把限界上下文全部拆成微服务** | 带来了巨大的运维、网络延迟和分布式事务负担 | 模块隔离是逻辑上的，单体架构内划分清晰的包结构同样能做好边界 |
| **把所有共享类都扔进 common 包** | common 变成毫无规律的大垃圾桶，牵一发而动全身 | 各自模块独立维护；只有纯粹的无业务通用工具才能放公共包 |

> [!TIP]
> 衡量设计好坏的唯一标准，**不是画了多少张架构图、建了多少个抽象类，而是业务规则是否能轻松看懂、修改时是否能快速定位且不产生意外副作用。**
