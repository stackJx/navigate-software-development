# 项目经验与知识沉淀规范

本模块用于在**代码开发完成、测试验证通过后**，将本次开发中沉淀出的高价值经验、非显然暗坑与架构决策留存在项目文档中，让经验随代码共同沉淀、团队共享，避免换个会话或换人接手就彻底遗失。

> [!IMPORTANT]
> **知识库是动态维护的“当前事实”，不是单纯追加的流水账**：
> - 针对已有主题的变动，采用**就地更新或合并**，不重复增加条目；
> - 已经过时的旧结论及时修正或删除；
> - 它不同于 `CHANGELOG.md`（按时间线记录发布版本改动），也不同于个人记忆（跨项目的私人备忘），它是属于**当前代码仓库的共享资产**。

<a id="1-适用性与跳过条件"></a>
## 1. 何时记录与跳过条件

本模块**默认开启**：每次产生代码变更的开发任务，在验证通过后均需评估“本次是否有值得沉淀的知识”。
**但默认开启绝不等于每次都要强行写一笔**——只有符合质量标准才记录，否则果断跳过。

### ✅ 应当写入的情况（同时满足）：
1. 本次开发确实修改了代码逻辑；
2. 遇到了非显然的技术暗坑、做出了关键架构决策，或明确了特殊的外部接口约束。

### ⏭️ 应当跳过的情况（不硬凑内容）：
1. 纯需求分析、方案探讨、只读调查等**未改动代码**的任务；
2. 改错字、改注释、微调前端文案等**极小改动**（除非改动本身揭示了一个重要的坑）；
3. 纯粹常规的 CRUD 开发，没有遇到任何暗坑，也没有特殊决策。

> **跳过时的处理**：在最终给用户的汇报中，在【本次沉淀】一栏简述“本次无可沉淀知识”及跳过理由即可，绝不强行编造无价值的废话。

<a id="2-什么算有价值"></a>
## 2. 什么内容值得记录（纳入与排除清单）

核心判断标准：**“离开代码本身就会丢失、且未来极可能被再次需要的信息。”**
问自己一句：**“下一个接手这块代码的人（或几个月后的自己）不知道这条，会不会踩坑或走弯路？”** 会，就记录；不会，就不记。

### ✅ 纳入清单（值得沉淀）：
- **关键架构与设计决策**：为什么这么做、放弃了哪些替代方案、在什么特定限制下才成立；
- **非显而易见的暗坑与陷阱**：踩过的坑、隐藏的模块耦合、特定平台的奇葩 Bug、看起来能改但实际上不能动的地方；
- **核心领域规则**：业务状态流转限制、边界计算口径（如“满减券门槛必须包含端点”）；
- **外部接口与第三方约束**：微信/支付宝等第三方接口的特殊行为、请求超时重试机制、数据迁移注意点；
- **重要的技术权衡**：在性能、数据一致性、可读性与改造成本之间权衡后的最终妥协与选择。

### ❌ 排除清单（坚决不记）：
- 看代码签名、目录结构或注释就能一目了然的事情（如“新增了 `getUserName` 方法”）；
- 临时的 TODO、任务进度备忘；
- Git Commit 或 CHANGELOG 里已经记录的琐碎提交信息；
- 显而易见的常规增删改查。

## 3. 文档位置与条目格式

### 文件位置
默认在目标代码仓库根目录下维护 `KNOWLEDGE.md` 文件。
若项目已有现成的文档目录约定（如 `docs/` 下的架构决策或设计文档），**优先遵循已有规范**，不自搞一套。

### 推荐的文档结构
按大主题分类，便于日后快速查阅：

```markdown
# 仓库知识库 (KNOWLEDGE.md)

## 关键技术决策
## 踩坑与特殊约束
## 业务领域规则
## 外部接口与依赖约束
```

### 推荐的条目格式
每条记录力求精炼、直指要害：

```markdown
### [主题名称]
- **背景与原因**：遇到了什么问题，或者为什么做出该决策；
- **核心结论**：系统当前的规定或解决方案是什么；
- **影响范围与注意点**：涉及到哪些文件/模块，改动时千万不能碰什么；
- **关联代码**：相关文件路径或 Issue/PR 链接。
```

<a id="4-写入去重与凝聚"></a>
## 4. 维护方式：更新、合并与清理

知识库不是只增不减的日志，而是**活文档**：

1. **同主题就地合并**：如果这次开发涉及的内容之前已经有记录，应直接更新或完善原条目，避免出现两条内容重叠但细节不一的条目；
2. **过时内容果断修正或删除**：如果原先记录的限制因为本次重构已经不再存在，必须同步修改或删掉过时条目，严禁留存误导他人的陈旧结论；
3. **少而精，拒绝臃肿**：宁可只有 5 条货真价实的避坑指南，也不要 50 条毫无信息量的流水账。

<a id="6-门禁产物与反例"></a>
## 5. 自查清单与避坑指南

### 5.1 自查清单（收尾核对）
- [ ] 仅记录了代码本身无法体现的决策、暗坑或业务规则；
- [ ] 没有记录“新增了某函数”等代码可自证的废话；
- [ ] 同主题内容已与旧条目合并，没有新增重复内容；
- [ ] 本次改动若推翻了旧规则，已同步更新或删除过时条目；
- [ ] 若无有价值的内容，已在最终汇报中写明跳过理由，未强行硬凑。

### 5.2 常见踩坑反例

| 常见反例 | 危害 | 正确做法 |
| --- | --- | --- |
| **连改个错字都要写一条知识库** | 知识库充斥大量垃圾信息，真正有价值的经验被淹没 | 无实际技术/业务增量时不写，最终汇报说明跳过理由 |
| **当成 CHANGELOG 堆砌流水账** | 越来越长、难以查阅，和 Git Log 重复 | 记录系统当前的事实与规则，同一主题就地更新而非无脑追加 |
| **复述代码函数名或类名** | 毫无信息量，代码改了文档容易过时 | 只写背后的意图（Why）与隐藏陷阱 |
| **旧决策推翻了，文档还留着旧规矩** | 严重误导后续开发人员 | 重构代码时同步更新或清理知识库文档 |
| **写泛泛而谈的编程鸡汤** | 与具体项目无关，没有实操价值 | 仅记录针对当前项目的具体决策与约束 |
