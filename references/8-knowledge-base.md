# 知识沉淀模块

本模块把每次开发中真正有价值、会长期复用的信息,收尾时凝聚进目标仓库的一个知识库文档,让知识随代码留存、随仓库共享,而不是随会话蒸发。**知识库是被持续凝聚的当前事实,不是 append-only 的流水账**——同一主题再次出现时更新/合并,过时的修正或删除。它与 CHANGELOG(按时间追加的变更记录)、CLAUDE.md/AGENTS.md(喂给 agent 的指令上下文)、个人 memory(跨项目的个人记忆)职责不同,不互相替代。

## 1. 适用性与跳过条件

本模块**默认开启**:每次产生代码变更的开发,在阶段 B 收尾(验证之后)都要评估"本次有没有值得沉淀的知识"。但**默认开启不等于每次都写**——只有过了 [§2 纳入清单](#2-什么算有价值)才落笔,否则写一句跳过理由。

**写入知识库(命中)**:本次产生了代码变更,且沉淀出至少一条 [§2](#2-什么算有价值) 纳入的耐久知识。

**跳过并写一句理由(不写)**:

- 纯需求分析、纯方案、只读调查等**不产生代码变更**的请求;
- 微变更快速通道(错别字、格式、纯重命名、展示文案等无行为变更),除非这次改动本身就是一条值得记的坑;
- 本次没有任何过纳入清单的信息——宁可不写,也不写没价值的条目。

跳过时在最终答复的「本次沉淀」里写明"本次无可沉淀知识"及一句理由,不留空、不硬凑。

## 2. 什么算有价值

判据是**"离开代码本身就会丢失、且未来会被再次需要"**。可判定地分为纳入与排除:

**纳入(命中任一即值得沉淀)**:

- **关键决策与理由**:为什么这么做、否决了哪个替代方案、在什么约束下成立(ADR-lite);
- **非显而易见的坑与约束**:踩过的坑、边界条件、隐藏耦合、"看起来能改其实不能"的地方;
- **领域规则与统一语言**:业务不变量、术语口径、状态迁移规则;
- **外部契约与依赖约定**:接口语义、幂等键来源、第三方行为、迁移与兼容注意;
- **关键取舍结论**:性能/一致性/兼容/成本之间做过的权衡与最终选择。

**排除(不写进知识库)**:

- 能被代码、目录结构、类型签名直接自证的信息;
- 一次性任务状态、临时 TODO、进度备忘;
- git 历史 / CHANGELOG / PR 描述已经记录的内容;
- 显而易见的 CRUD、无争议的常规实现。

判断某条信息该纳入还是排除时,问一句:**"下一个接手的人(或下一次的自己)不知道这条,会不会踩坑或走弯路?"** 会,就纳入;不会,就排除。

## 3. 文件位置与条目结构

**位置**:默认在目标仓库根新建/维护单一文件 `KNOWLEDGE.md`。若仓库已有约定(如 `docs/` 下的知识或决策目录、或已用 `CLAUDE.md`/`AGENTS.md` 集中承载团队知识),**优先复用既有约定**,不另起一套。不把知识库塞进会被 agent 每次自动加载的上下文文件里撑大常驻开销,除非项目本就如此约定。

**文件结构**:顶部按稳定主题分节,便于长期检索与凝聚:

```text
# 仓库知识库

## 关键决策
## 约束与坑
## 领域规则与统一语言
## 外部契约与依赖
```

**条目结构**:每条精简但可追溯,建议字段(按复杂度缩放,简单条目可一到两行):

| 字段 | 内容 |
| --- | --- |
| 日期 | 沉淀日期(由用户/环境提供,不臆造) |
| 触发 | 对应的需求/用例/开发切片 |
| 结论 | 一句话说清"是什么"(决策/规则/坑) |
| 理由 | 为什么这样、否决了什么(决策类必填) |
| 影响 | 影响范围、适用边界、失效条件 |
| 追溯 | 相关文件/符号/PR/issue 链接(有则给) |

条目表达"当前事实",不是变更叙事;写"系统现在是什么样、为什么",而不是"我这次改了什么"(后者是 CHANGELOG 的职责)。

## 4. 写入、去重与凝聚

知识库是**活文档**,维护动作不止"新增":

- **新增**:主题在库中不存在 → 追加到对应主题分节。
- **更新/合并**:同一主题已有条目 → 就地更新,合并新信息,不新增内容重叠的第二条。
- **修正/删除**:既有条目被本次变更推翻或已过时 → 修正或删除,不保留会误导人的旧结论。
- **凝聚**:多条零散条目指向同一主题时,合并成一条更清晰的;宁可少而准,不要多而杂。

写入前先读现有 `KNOWLEDGE.md`(或既有知识文件),定位同主题条目,决定新增/更新/删除,不盲目 append。写入本身是阶段 B 的变更动作,须在开发前合同发出之后进行(与其他写操作同规则)。

## 5. 与追踪链及其他模块的衔接

- **追踪链**:沉淀是主路由「跨阶段追踪」链的末端——`需求/用例 → 模块/上下文 → 开发切片 → 测试 → 代码 → 验证证据 → 知识沉淀`。每条知识条目应能追溯到触发它的需求或切片,不写游离于本次工作之外的泛化结论。
- **DDD 命中时**:统一语言、聚合不变量、上下文边界与跨边界一致性决策是天然的沉淀来源(领域规则 / 关键决策)。
- **TDD 命中时**:被回归用例锁定的行为契约、复现过的缺陷根因,是"约束与坑"的高价值来源。
- **Git Flow 命中时**:分支/合并/保护的团队约定若尚未在仓库文档化,可沉淀为团队约定,避免每次重问。
- **委派命中时**:各子代理产出的知识由主智能体扇入去重后统一写库,不各写各的、不重复入库。
- **与 memory(如 Claude Code)**:仓库知识库是团队共享、随仓库版本化的持久层;个人 memory 是跨项目的个人记忆。仓库级、可共享的知识入库,不写进个人 memory;反之亦然,不重复。

## 6. 门禁、产物与反例

### 6.1 交付门禁

本节只列知识沉淀的**专有**门禁;跨模块通用项见主路由的「开发前合同自检表」。完成前检查:

- 本次若产生代码变更,已评估是否有可沉淀知识,并据 [§2](#2-什么算有价值) 决定写或跳过;
- 写入的每条都过纳入清单,无排除清单里的噪音(复述代码、一次性状态、CHANGELOG 已记录);
- 同主题已有条目时是更新/合并,而非新增重复条目;
- 被推翻或过时的旧条目已修正或删除;
- 每条可追溯到需求/切片;
- 跳过时在最终答复写明"本次无可沉淀知识"及一句理由,不留空、不硬凑。

### 6.2 产物

在最终答复的「本次沉淀」项报告(按复杂度缩放):

1. 写入/更新/删除了哪些知识条目(或"本次无可沉淀知识"及理由);
2. 落位的知识库文件路径。

### 6.3 常见反例及修正

| 反例 | 问题 | 修正 |
| --- | --- | --- |
| 每次都写、错别字也记 | 知识库被噪音淹没 | 过 §2 纳入清单才写,无价值则跳过写理由 |
| 把知识库当变更流水账 | 与 CHANGELOG 重复、越堆越乱 | 写当前事实,同主题更新而非追加 |
| 复述函数签名/目录结构 | 代码已自证,条目无信息量 | 只写离开代码会丢失的知识 |
| 同一主题堆多条 | 检索困难、结论冲突 | 凝聚合并成一条 |
| 旧结论被推翻仍保留 | 误导下一个接手的人 | 修正或删除过时条目 |
| 灌进 CLAUDE.md 撑大上下文 | 抬高每次 context 成本 | 用仓库专用知识文件,除非项目已约定 |
| 写游离于本次工作的泛化大道理 | 无法追溯、不可验证 | 只沉淀能追溯到需求/切片的具体知识 |

知识沉淀的最终标准不是条目多寡,而是:**离开代码会丢失、未来会被再次需要的知识,被准确、可追溯、去重地留在了仓库里。**
