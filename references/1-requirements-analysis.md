# 需求分析规范

## 目标

把模糊的想法梳理成明确、有边界、可验证的具体需求。本模块是开发前必须执行的第一步；梳理完成后继续形成开发思路与验收标准，并在改动代码前向用户汇报，严禁先改代码再补写需求。

## 1. 明确需求背景与范围

先查阅用户提出的诉求，并结合当前项目的代码、既有接口、数据结构和已有文档，明确以下五点：

- **核心价值**：这个功能做完后，能为用户或业务带来什么实际效果？解决什么问题？
- **本次范围**：明确划定“本次必须做”、“后续再考虑”和“本次明确不做”的界限；
- **现有事实**：系统中已有现成的哪些功能、接口或规则？避免重复开发；
- **疑问与假设**：有哪些关键问题需要用户拍板？有哪些非关键细节可以先按常理假设（并明确告知用户）；
- **统一术语**：同一个概念在项目中使用统一命名，避免每个人叫法不同产生误解。

## 2. 按“角色—数据—操作”梳理核心逻辑

### 角色（谁来用）

明确发起者是普通用户、管理员、外部第三方系统还是后台定时任务。搞清楚每个角色的职责范围、数据可见性与操作权限。

### 数据（操作什么）

先把涉及的数据作为业务概念来理解，不要过早直接绑定到数据库表字段。关注：

- 数据的实际业务含义与所属模块；
- 数据与其他实体之间的关联关系；
- 数据的生命周期、状态流转与约束限制；
- 是否包含敏感信息（如密码、手机号）或需要遵循外部合规要求。

### 操作（做什么）

普通的增删改查如实说明即可；核心业务操作尽量使用精准的动词（如“提交审核”、“扣减库存”、“申请退款”）。搞清每个操作的前置条件、权限校验、状态变化、副作用（如发通知、写审计日志）、失败时的处理，以及是否需要防止重复提交。

## 3. 梳理业务场景与用例

梳理场景时，推荐使用简明通俗的句式：

> **谁**，在**什么前提条件**下，对**什么数据**执行了**什么操作**，触发了**什么状态变化或副作用**，最终**看到什么结果**。

| 要素 | 说明 |
| --- | --- |
| 用例编号与目标 | 简短编号及要完成的业务目标 |
| 发起角色 | 谁在操作，需要什么权限 |
| 前置条件 | 当前数据状态、登录状态或依赖的外部条件 |
| 操作对象 | 被操作的数据实体或资源 |
| 业务动作 | 执行了什么具体动作 |
| 状态与副作用 | 数据状态改变、异步事件、发送消息通知等 |
| 最终结果 | 页面展示、接口返回值或数据持久化结果 |
| 异常与边界 | 越权访问、非法输入、外部服务故障、重复提交等 |

编写用例时，除了正常的成功流程外，至少还要覆盖以下场景：
- 未登录或权限不足；
- 必填项缺失、格式错误或超出边界值；
- 目标数据不存在；
- 当前状态不允许执行（如“已退款的订单无法再次发货”）；
- 用户快速连续点击或重复请求；
- 关键副作用未意外触发（如“付款失败时不应扣减库存”）。

## 4. 转化为可核验的验收标准

为每个核心用例编写明确具体的验收条件，推荐使用清晰的 Given / When / Then 格式：

```text
Given（前提） 某个用户身份、初始数据状态或外部环境
When （操作） 执行某个具体的业务动作
Then （结果） 验证返回的结果、界面展示、数据状态变化及触发的通知
And  （防范） 验证绝不能出现的意外变更（如“账户余额不得扣成负数”）
```

验收标准必须**非是即否、结果明确**，任何人都能直接据此判断是否通过。严禁使用“功能正常”、“体验良好”、“速度很快”等主观模糊字眼；若有性能要求，必须给出具体的数值指标（如“单页 100 条数据加载时间 < 500ms”）。

## 5. 考虑通用非功能要求（按需）

根据任务的实际影响，评估是否需要关注以下方面：
权限安全、防重复提交（幂等）、并发冲突处理、数据一致性、操作日志审计、系统监控、向下兼容性、旧数据迁移、失败回滚等。

<a id="门禁"></a>
## 自查清单（门禁）

在向用户输出需求分析前，确认已满足以下条件：

- [ ] 核心目标清晰，本次做与不做的界限明确；
- [ ] 关键操作有明确的角色权限，数据概念有明确归属；
- [ ] 正常流程和常见异常边界（非法输入、越权、重复操作）都有覆盖；
- [ ] 状态流转清晰完整，没有遗漏死角；
- [ ] 区分了已有事实与推论，关键业务疑问已向用户提出，未擅自拍板；
- [ ] 验收标准明确具体，可以直接核验。

## 输出要求

在开始修改代码前，向用户输出的方案中必须包含：

- `## 需求分析`：目标背景、范围界定、业务场景与用例、通用约束、待确认事项；
- `## 验收标准`：从场景中提取的具体验收条件（可核验的 Given/When/Then 或清单）。

注：内容篇幅可按任务大小灵活调整。简单的改动可以合并简写，重点讲清目标、范围、关键逻辑和验收条件；若已有现成的需求文档，可以引用但必须提炼出本次涉及的结论，不能只丢一个链接。
