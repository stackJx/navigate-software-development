## 1. 核心目标与基本原则

测试驱动开发的核心理念：**在改动代码前，先写一个能精准证明该功能或问题的自动化测试用例。**
特别是在**修复 Bug** 时，必须先写一个能够稳定复现该缺陷的失败测试（作为永久回归防范），再动手修复。

### 核心准则（遵循 Google 测试最佳实践）
1. **测试业务行为，而非实现细节**：测试关注“输入什么、返回什么、产生什么实际业务效果”，不要测试类的内部私有变量或私有方法，避免实现一变测试就全崩（脆弱测试）。
2. **状态优先，克制 Mock**：优先验证最终数据状态（State Verification），不要为了测试写一堆复杂的 Mock 交互断言（Interaction Verification）。
3. **保持测试独立与确定性（Hermetic）**：单元测试绝不发起真实的网络请求、不访问外部第三方服务；每次运行结果必须完全确定，拒绝不稳定的偶现测试（Flaky Tests）。
4. **意图清晰高于盲目去重（DAMP 优于 DRY）**：测试代码允许适度的样板重复，重点是让人打开测试文件一眼就能看懂“前因后果”，不要过早抽象复杂的继承和辅助函数，导致看测试像在看谜题。
5. **不为了覆盖率而写无意义测试**：只测真正的业务规则、权限校验、边界条件和潜在风险，拒绝无脑对 getter/setter 刷覆盖率。

## 2. TDD 核心循环：红-绿-重构

TDD 的标准循环由三步组成，每次只推进一个小功能或一个 Bug 修复：

```text
编写失败测试 (RED) → 编写刚好让测试通过的代码 (GREEN) → 优化与重构 (REFACTOR)
```

### 第一步：红灯（RED）—— 编写失败测试
- **写测试前先跑既有测试**：确认当前已有测试全部是绿的，避免把旧有的报错误当成是本次的测试失败；
- **写出能够精准复现问题的测试用例**：
  - 测试用例必须能独立运行；
  - 失败原因必须是“期望的功能尚未实现”或“Bug 触发了断言失败”；
  - ❌ *无效红灯*：因为语法错误、缺少 import、测试环境不通等导致的报错不算有效红灯。

### 第二步：绿灯（GREEN）—— 最快跑通测试
- 只写刚好能让当前测试通过的生产代码，不要在此刻提前写一堆未来的逻辑；
- **严禁作弊**：
  - 严禁通过故意调低断言要求、注释掉测试用例或吃掉异常来换取测试通过；
  - 业务逻辑必须在服务端/核心层真实实现，不能靠在前端隐藏按钮来“假装修复”。

### 第三步：重构（REFACTOR）—— 优化与清理
- **只在测试全绿时重构**：测试通过后，清理冗余代码、改善命名、提取重复逻辑；
- 每次重构一小步，立即重跑测试，确保外部行为和业务逻辑完全没有被破坏。

## 3. 测试分层：选择合适的测试层级

根据问题风险选择最低成本、反馈最快的层级，不需要机械追求固定比例：

| 测试类型 | 验证重点 | 运行环境与依赖 |
| --- | --- | --- |
| **单元测试 (Unit)** | 纯业务算法、复杂公式、状态机流转、对象校验 | 极快（毫秒级），纯内存运行，不启框架，不连数据库/网络 |
| **集成/组件测试 (Integration)** | 数据库读写（ORM/Repository）、外部接口适配、配置解析 | 访问测试专用的轻量数据库（如 SQLite 或隔离的测试容器），验证数据真实持久化 |
| **接口/功能测试 (API/Feature)** | HTTP 路由、参数校验、中间件拦截、权限鉴权、返回格式 | 启动应用内核，调用真实接口并检查响应与测试数据库结果 |
| **端到端测试 (E2E)** | 跨越前端页面与后端的关键主流程（如用户注册-下单-支付闭环） | 真实浏览器或驱动，数量要少，只覆盖最重要的核心业务路径 |

> [!TIP]
> 绝大多数业务规则和 Bug 修复，应优先在**单元测试**或**轻量集成测试**中解决；运行速度越快，反馈越及时。

## 4. 测试命名规范（表达业务意图）

测试用例的名称应当像一份**可执行的业务说明书**。任何人即使不看实现代码，只看测试名称和输出，就能知道业务规则是什么。

### 常用命名模板
```text
[角色/主体]_[在什么场景或条件下]_[预期产生什么行为或结果]
```

### 推荐示例
- ✅ `user_cannot_withdraw_amount_greater_than_balance`（用户提现金额超过余额时应当被拒绝）
- ✅ `order_total_applies_20_percent_discount_when_using_coupon`（使用满减券时订单总额应享受 20% 优惠）
- ✅ `duplicate_submit_order_creates_only_one_order`（重复提交订单时仅创建一条订单记录）
- ✅ `non_admin_user_is_forbidden_to_delete_products`（非管理员删除商品应返回 403 权限不足）

### 避免的不良命名
- ❌ `test_order`（毫无意义）
- ❌ `test_success` / `test_happy_path`（完全不知道在测什么业务）
- ❌ `test_method_abc_line_50`（绑定了内部实现细节）

## 5. 测试结构：Arrange-Act-Assert

编写测试代码时，统一采用经典的 **AAA**（或 Given-When-Then）结构，用空行隔开三阶段：

```text
Arrange（准备）：准备测试所需的最少数据、参数与初始状态
Act    （执行）：调用被测试的核心方法或触发一个业务动作
Assert （断言）：核验返回结果、数据库变更或触发的重要通知
```

### 断言技巧
1. **优先断言关键业务字段**：不仅要断言返回了 `200`，更要断言返回结果里的关键数据（如订单状态变为 `PAID`、扣减后的余额正确）；
2. **断言负向防范**：对于失败场景（如扣款失败），除了验证报错信息，还要断言**“禁止产生副作用”**（如数据库中未生成订单、余额未扣减）；
3. **一个用例聚焦一个逻辑点**：不要把十几个互不相关的场景杂糅在一个测试方法里，拆分成独立的测试更容易排查失败原因。

## 6. 测试替身使用指南（Stub / Fake / Spy / Mock）

遇到耗时慢、不可控或外部网络依赖时，才使用测试替身（Test Doubles），不要滥用：

| 替身类型 | 白话解释 | 适用场景 | 注意事项 |
| --- | --- | --- | --- |
| **Stub（打桩）** | 提供固定的假返回值 | 比如模拟“获取天气接口”返回晴天 | 仅用于给测试提供预设输入，不用于验证调用次数 |
| **Fake（伪造实现）** | 内存版的轻量替代品 | 比如用内存 Map 代替真实 Redis、用 Fake 发信器收集邮件 | 推荐优先使用 Fake，能保证测试确定且贴近真实 |
| **Spy（间谍）** | 记录真实函数的调用记录 | 比如记录“短信发送函数被调用了 1 次，参数是手机号 138xxx” | 验证调用参数时使用 |
| **Mock（严格模拟）** | 预先设定“必须被以特定参数调用几次” | 比如必须调用外部扣款接口一次 | 慎用！过度使用 Mock 会让测试严重耦合内部实现 |

**红线**：单元测试严禁真正发起外部 HTTP 请求或真实发邮件。

## 7. 高频场景测试指南

### 1. 权限与身份校验
- 分别覆盖：未登录游客、已登录普通用户、资源拥有者、管理员；
- 断言权限拦截在真正的业务修改之前生效；被拦截时数据和状态必须保持原样。

### 2. 防重提交与并发（幂等性）
- 模拟同一用户连续发起两次相同的请求；
- 断言最终只生成一条业务记录，第二次请求返回幂等成功或明确提示，系统不报错崩溃。

### 3. 分页与条件筛选
- 准备包含命中条件的数据和不应命中的“干扰数据”；
- 验证结果中只包含目标项，不泄露其他用户或未发布的数据；
- 验证分页页码、每页数量与总数准确。

### 4. 异步队列与消息发送
- 分两步验证：① 业务执行后是否正确投递了消息任务；② 消费该任务后是否产生最终期望的业务结果。

### 5. 外部第三方接口调用
- 使用 Fake 适配器模拟接口成功、超时、返回业务错误码（如“余额不足”）等不同场景，确保本系统都有合理的容错处理。

## 8. 验证阶段与自查清单

在提交代码前，按以下顺序逐步跑测试验证：

1. **当前聚焦测试**：运行本次修改针对的单元测试，必须全绿；
2. **当前模块测试套件**：运行改动模块的所有测试，确保没有破坏现有功能；
3. **全量快速测试**：提交前跑一次项目全部单元测试；
4. **CI 持续集成构建**：确保在标准 CI 环境下构建与自动化测试全绿。

### 提交前自查清单：
- [ ] 针对本次新增行为或 Bug 修复，已有明确的自动化测试覆盖；
- [ ] Bug 修复留下了能永久防止问题回归的测试用例；
- [ ] 测试名称清晰明了，表达了真实的业务意图；
- [ ] 测试用例没有调用真实外网接口，运行速度快且结果稳定；
- [ ] 没有为了跑通测试而注释掉旧测试或故意弱化断言；
- [ ] 本地与 CI 自动化测试全部绿色通过。

## 9. 常见踩坑反例

| 常见反例 | 危害 | 正确做法 |
| --- | --- | --- |
| **先写完所有代码，最后补测试** | 测试变成了应付差事的工具，无法引导设计，容易遗漏边界 | 先写失败测试明确预期，再写代码实现 |
| **测试只断言 HTTP 状态码 200** | 接口报错但因为有全局兜底返回了 200，Bug 被隐藏 | 必须断言返回体中的关键业务字段与持久化数据 |
| **为了让测试通过，注释掉原来的断言** | 掩耳盗铃，彻底失去防护作用 | 查明原因，修复真实代码缺陷 |
| **大量使用复杂的 Mock** | 稍微重构一下内部私有方法，测试全挂，维护成本极高 | 尽量测公开输入和最终状态，减少对内部调用的 Mock |
| **测试依赖执行顺序** | 必须先跑 TestA 才能跑 TestB，单跑某一个会挂 | 每个测试独立准备数据和清理现场，互不干扰 |
| **使用死等 `sleep(3)` 测试异步逻辑** | 极大拖慢测试速度，且在不同性能机器上偶现失败 | 采用轮询判断条件成立或 Fake 同步驱动 |
