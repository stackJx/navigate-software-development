# 开发思路与规划规范

## 目标

把已确认的需求转化为步骤清晰、可验证、易交付的实施计划。本模块是开发前必须执行的第二个必选阶段，在需求分析完成后进行；若涉及领域设计（DDD）或版本控制（Git Flow），在此阶段将相关决策融合进开发步骤中。

---

## 1. 梳理现有代码与定位缺口

在动手写新代码之前，必须先看懂现有代码，建立对应关系：

```text
业务用例 → 现有的对应模块/文件 → 当前代码行为 → 本次需要补充或改造的缺口
```

- **查明现有能力**：项目中是否有现成的类、函数或工具方法可以直接复用？
- **明确影响面**：本次改动会影响哪些既有接口、数据库表或上游调用方？
- **拒绝凭空盲猜**：任何计划都必须基于具体的已有文件和代码现状，不靠脑补写计划。

---

## 2. 代码落位与模块职责划分

当明确要改代码时，按以下优先级决定代码写在哪个位置，**优先复用既有模块，避免盲目新建**：

1. **优先在现有模块上扩展**：如果既有模块能够自然承载此业务，直接在其基础上增加功能，保持单一职责。
2. **确实是全新业务概念时再新建模块**：只有属于全新的独立业务域时才新建目录/包，并明确新模块的职责边界（管什么、不管什么）。
3. **流程编排下沉到应用层**：如果需要串联多个独立模块完成一个长操作，在应用层（Application Service / Use Case）增加一个流程编排入口，不要让底层模块互相强耦合。
4. **拒绝入口文件膨胀**：如果 Web Controller 或路由处理函数里堆积了大量业务判断和 SQL 调用，应及时将核心业务逻辑下沉到业务层或领域层。

---

## 3. 梳理执行步骤与依赖关系

将开发任务拆解为若干个小步，并理清它们之间的先后顺序：

- **基础能力先行**：先实现底层核心算法或数据模型，再写上层调用接口与前端展示；
- **提前暴露高风险**：第三方外部接口调用、复杂算法验证、历史数据迁移等不确定性高的步骤优先验证；
- **避免循环依赖**：如果模块 A 依赖模块 B，模块 B 又依赖模块 A，必须重新审视设计，通过接口抽象或拆分来解耦；
- **横切关注点同步跟进**：权限校验、操作审计、日志监控等，应随对应功能一起实现，不要统一拖延到最后堆积。

---

## 4. 代码实现与注释规范（Google 风格）

为了保证代码具备高可读性、高可维护性并符合工业级标准，所有代码编写与重构均须遵循 Google 工程实践规范：

### 4.1 代码注释规范（Google Style Guide）

- **解释 Why（为什么这么做），而不是复述 What（代码在做什么）**：
  代码本身应清晰自解释（命名精准、逻辑直观）；注释重点解释**业务背景、设计意图、权衡考量或规避暗坑的原因**。
  - ❌ *不推荐*：`i += 1 // i 加 1`
  - ✅ *推荐*：`// 微信支付接口对于退款金额限制必须大于 0，此处做防御性兜底防止第三方 SDK 异常`
- **公共 API 与核心函数必须提供标准文档注释**：
  包含功能概述、参数说明（Args）、返回值（Returns）、可能抛出的异常/错误（Raises/Errors）及调用前提条件。
- **暗坑与临时 Workaround 必须注明背景**：
  遇到特定框架 Bug、平台兼容性问题或不得不做的特殊处理时，注释必须附带上下文说明或 Issue 链接。
- **杜绝废弃的“尸体代码”**：
  严禁把大段废弃不用的代码用 `//` 注释后留存在源文件中。版本历史交给 Git 管理，源码文件必须保持干净。
- **代码变动与注释同步**：
  修改或重构代码逻辑时，必须同步更新或删除对应的注释，严禁出现注释与代码实际行为不符的情况。
- **标准 TODO 格式**：
  统一采用 Google 规范格式：`// TODO(username): 说明待办事项的具体内容及后续改进计划`。

### 4.2 设计模式使用规范（Google Engineering Practices）

- **实用克制，简单优先（Simplicity over Cleverness）**：
  **永远优先选择最简单直接、易读易懂的写法**。拒绝过度工程化（Over-engineering），严禁为了“炫技”而生搬硬套设计模式。能用一个纯函数清晰表达的，绝不新建复杂的类层级；能用简单 if-else 解决的，绝不搞策略工厂。
- **组合优于继承（Composition over Inheritance）**：
  优先通过对象组合与接口委托来扩展能力，避免建立深层、脆弱的继承树。
- **三次法则（Rule of Three）**：
  不要为了臆想中“未来可能会扩展”而提前做多层抽象。仅当出现两个以上明确、已发生的具体业务场景时，才进行通用模式的抽象与重构。
- **单向直白的数据依赖**：
  调用链条应当尽量保持单向流动，避免出现复杂的双向联动或隐式全局状态传递。

---

## 5. 制定最小可用版本（MVP）

如果需求较为复杂，需要划分轻重缓急，分批交付：
- **核心闭环必须具备**：核心业务价值、安全权限、数据准确性和必要的异常恢复机制，绝不能以“这只是第一版”为理由被砍掉；
- **次要体验可后置**：复杂的筛选条件、批量导出、个性化配置等非核心诉求，可在后续阶段迭代。

---

## 6. 拆解为可验证的实现步骤

每个实施步骤都应该是一个**小闭环**：
1. **步骤名称**：要做什么具体改动；
2. **涉及文件**：改动哪些模块、接口或数据模型；
3. **验证方式**：通过哪个测试命令、接口测试或页面操作进行核验；
4. **潜在风险**：是否影响兼容性、是否有并发或数据迁移风险。

## 自查清单（门禁）

在向用户输出开发思路前，确认已做到：

- [ ] 计划直接引用了现有代码中的真实文件与类，而非凭空套用模板；
- [ ] 明确了代码落位的理由，优先复用现有能力而非盲目新建；
- [ ] 步骤拆解清晰，逻辑顺序符合依赖关系（基础能力在先，上层组装在后）；
- [ ] 关键技术风险（如第三方外部接口、数据迁移、并发）已有应对策略；
- [ ] 代码注释与实现遵循 Google 风格（解释 Why、克制使用模式、无冗余抽象）；
- [ ] 每个步骤都有明确具体的验证手段。

---

## 输出要求

在动手修改代码前，向用户输出的方案中必须使用固定二级标题 `## 开发思路`。

### 必包含的四大核心内容（任何任务都不能省略）：

1. **现状与缺口**：现有代码在哪里、目前是什么逻辑、本次需要改动/补充什么；
2. **实现范围与落位**：具体修改哪些文件/模块，为什么代码放在这里；
3. **分步实现计划**：按先后顺序排列的具体实施步骤，标出依赖关系与可并行的工作；
4. **验证方式与风险说明**：每一步怎么验证正确性，潜在风险（如兼容性、数据迁移、边界异常）如何防范。

### 按需补充的内容（仅在涉及对应场景时提供）：

- **领域设计方案（DDD）**：当涉及复杂业务建模时，简要说明选用的模型与边界；未选用时用一句话说明理由（如“增删改查薄规则，跳过 DDD”）；
- **测试驱动策略（TDD）**：当涉及 Bug 修复或核心逻辑时，说明测试用例先行顺序；未选用时用一句话说明理由；
- **版本控制策略（Git Flow）**：当用户明确要求分支/提交规范时在此说明；未要求时用一句话说明跳过理由。
