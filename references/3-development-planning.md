# 开发思路与规划规范

## 目标

把已确认的需求转化为步骤清晰、可验证、易交付的实施计划。本模块是开发前必须执行的第二个必选阶段，在需求分析完成后进行；若涉及领域设计（DDD）或版本控制（Git Flow），在此阶段将相关决策融合进开发步骤中。

---

## 1. 梳理现有代码与定位缺口

在执行写入操作前，先核对已有代码与项目约定，建立对应关系；空项目或全新功能如实注明尚无对应实现：

```text
业务用例 → 现有的对应模块/文件 → 当前代码行为 → 本次需要补充或改造的缺口
```

- **查明现有能力**：项目中是否有现成的类、函数或工具方法可以直接复用？
- **明确影响面**：本次改动会影响哪些既有接口、数据库表或上游调用方？
- **区分现状与拟建**：涉及已有项目的计划以核实的文件、接口和行为为依据；尚不存在的文件、模块或接口明确标为拟建，不伪称已有能力，也不因空项目而阻塞规格设计。

---

## 2. 代码位置与模块职责划分

当明确要改代码时，按以下优先级决定代码写在哪个位置，**优先复用既有模块，避免盲目新建**：

1. **优先在现有模块上扩展**：如果既有模块本身的职责涵盖此类业务，直接在其基础上增加功能，保持单一职责。
2. **确实是全新业务概念时再新建模块**：只有属于全新的独立业务域时才新建目录/包，并明确新模块的职责边界（管什么、不管什么）。
3. **流程编排放到应用层**：如果需要串联多个独立模块完成一个长操作，在应用层（Application Service / Use Case）增加一个流程编排入口，不要让底层模块互相强耦合。
4. **拒绝入口文件膨胀**：如果 Web Controller 或路由处理函数里堆积了大量业务判断和 SQL 调用，应及时将核心业务逻辑拆分到业务层或领域层。

---

## 3. 梳理执行步骤与依赖关系

将开发任务拆解为若干个小步，并理清它们之间的先后顺序：

- **基础能力先行**：先实现底层核心算法或数据模型，再写上层调用接口与前端展示；
- **提前暴露高风险**：第三方外部接口调用、复杂算法验证、历史数据迁移等不确定性高的步骤优先验证；
- **避免循环依赖**：如果模块 A 依赖模块 B，模块 B 又依赖模块 A，必须重新审视设计，通过接口抽象或拆分来解耦；
- **通用跨模块逻辑同步跟进**：权限校验、操作审计、日志监控等通用逻辑，应随对应功能一起实现，不要统一拖延到最后堆积。

---

## 4. 代码实现与注释规范（项目约定优先）

代码实现与注释优先遵循项目已有规范、格式化配置及相邻代码约定。项目没有约定时，再参考当前语言的常见形式或对应的 Google 风格指南；本节不要求迁移既有风格，也不统一不同技术栈的注释语法。

### 4.1 代码注释规范

- **解释 Why（为什么这么做），而不是复述 What（代码在做什么）**：
  代码本身应清晰自解释（命名精准、逻辑直观）；注释重点解释**业务背景、设计意图、权衡考量或规避暗坑的原因**。
  - ❌ *不推荐*：`i += 1 // i 加 1`
  - ✅ *推荐*：`// 微信支付接口对于退款金额限制必须大于 0，此处做防御性检查防止第三方 SDK 异常`
- **公共 API 与核心函数按项目约定提供文档注释**：
  沿用项目的注释格式与文档工具，按调用者需要说明功能、参数、返回值、错误和前提条件；没有约定时使用当前语言的常见形式，不强制套用 `Args`、`Returns` 等特定格式，也不机械补齐不适用的条目。
- **暗坑与临时 Workaround 必须注明背景**：
  遇到特定框架 Bug、平台兼容性问题或不得不做的特殊处理时，注释必须附带上下文说明或 Issue 链接。
- **杜绝废弃的“尸体代码”**：
  严禁把大段废弃不用的代码用 `//` 注释后留存在源文件中。版本历史交给 Git 管理，源码文件必须保持干净。
- **代码变动与注释同步**：
  修改或重构代码逻辑时，必须同步更新或删除对应的注释，严禁出现注释与代码实际行为不符的情况。
- **TODO 沿用项目格式**：
  写清待办内容与解决条件，按已有约定关联负责人或 Issue；没有约定时可用 `TODO: 待办内容及解决条件`，注释语法随语言调整。负责人或 Issue 必须有真实依据，不为凑格式虚构用户名或链接。

### 4.2 设计模式使用规范

- **实用克制，简单优先（Simplicity over Cleverness）**：
  **永远优先选择最简单直接、易读易懂的写法**。拒绝过度工程化（Over-engineering），严禁为了“炫技”而生搬硬套设计模式。能用一个纯函数清晰表达的，绝不新建复杂的类层级；能用简单 if-else 解决的，绝不搞策略工厂。
- **组合优于继承（Composition over Inheritance）**：
  优先通过对象组合与接口委托来扩展能力，避免建立深层、脆弱的继承树。
- **三次法则（Rule of Three）**：
  不要为了臆想中“未来可能会扩展”而提前做多层抽象。仅当出现两个以上明确、已发生的具体业务场景时，才进行通用模式的抽象与重构。
- **单向直白的数据依赖**：
  调用链条应当尽量保持单向流动，避免出现复杂的双向联动或隐式全局状态传递。

---

## 5. 制定最小可用版本（MVP）

如果需求较为复杂，需要划分轻重缓急，分批交付：
- **核心主流程必须完整**：核心业务价值、安全权限、数据准确性和必要的异常恢复机制，绝不能以“这只是第一版”为理由被砍掉；
- **次要体验可后置**：复杂的筛选条件、批量导出、个性化配置等非核心诉求，可在后续阶段迭代。

---

## 6. 拆解为可验证的实现步骤

每个实施步骤都应该是一个**独立可验证的小单元**：
1. **步骤名称**：要做什么具体改动；
2. **涉及文件**：改动哪些模块、接口或数据模型；
3. **验证方式**：通过哪个测试命令、接口测试或页面操作进行核验；
4. **潜在风险**：是否影响兼容性、是否有并发或数据迁移风险。

需要保存规格文档或持续交接时，用稳定任务编号（如 `T-1`）将这些步骤关联到验收项（`AC-1` 等），并写明依赖关系、负责的文件、当前状态与验证证据。一个任务可以覆盖多个验收项，一个验收项也可以由多个任务共同完成，不必为了形式上的“一一对应”拆出多余的碎片步骤。只有在核对实际文件与修改（含代码、配置、测试与文档）以及验证证据符合要求后，才能标记为完成，未执行或失败的验证如实记录。

当业务范围、接口或行为约定、或验收要求发生实质变化时，暂停受影响的所有写入操作（含代码、配置、测试与文档），先按规范向用户输出修订后的三项方案与更新规格文档，再调整受影响的任务；如果只是细化执行顺序或代码放置位置，可以直接更新计划记录，无需额外增加审批。接续中断的任务时，先核对当前规格修订版本、实际文件差异（diff，含代码、配置、测试与文档）、已有成果以及旧验证是否依然适用，再安排剩余步骤。具体记录格式见 [SDD 规格与任务追踪](9-spec-driven-development.md)。

## 自查清单

在向用户输出开发思路前，确认已做到：

- [ ] 计划所引用的已有文件与接口经过核实；尚不存在的部分标为拟建，事实与设计建议没有混淆；
- [ ] 明确了代码放在哪里的理由，优先复用现有能力而非盲目新建；
- [ ] 步骤拆解清晰，逻辑顺序符合依赖关系（基础能力在先，上层组装在后）；
- [ ] 关键技术风险（如第三方外部接口、数据迁移、并发）已有应对策略；
- [ ] 代码实现、API 注释和 TODO 沿用项目约定；无约定时才参考当前语言的常见形式或 Google 风格，未借此改写无关代码风格；
- [ ] 每个步骤都有明确具体的验证手段。

---

## 输出要求

在执行任何写入操作前，向用户输出的方案中必须使用固定二级标题 `## 开发思路`。

### 必包含的四大核心内容（任何任务都不能省略）：

1. **现状与缺口**：现有代码在哪里、目前是什么逻辑、本次需要改动/补充什么；
2. **实现范围与代码位置**：具体修改哪些文件/模块，为什么代码放在这里；
3. **分步实现计划**：按先后顺序排列的具体实施步骤，标出依赖关系与可并行的工作；
4. **验证方式与风险说明**：每一步怎么验证正确性，潜在风险（如兼容性、数据迁移、边界异常）如何防范。

### 按需补充的内容（仅在涉及对应场景时提供）：

- **领域设计方案（DDD）**：当涉及复杂业务建模时，简要说明选用的模型与边界；未选用时用一句话说明理由（如“增删改查薄规则，跳过 DDD”）；
- **测试驱动策略（TDD）**：当涉及 Bug 修复或核心逻辑时，说明测试用例先行顺序；未选用时用一句话说明理由；
- **版本控制策略（Git Flow）**：当用户明确要求分支/提交规范时在此说明；未要求时用一句话说明跳过理由。
- **规格与交接**：需要保存文档时，说明沿用或新建的文件路径、当前修订版本及任务与验收条件的对应关系；简单任务直接在对话中输出三项即可，不会因为采用 SDD 就强制新建文件、增加额外审批或执行 Git 操作。
