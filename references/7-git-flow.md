# 版本控制与 Git 分支提交规范

本模块用于在用户**明确提出版本控制相关要求**时，在动手改代码前确定分支模型、提交（Commit）规范与合并策略。
**核心原则：除非用户明确要求，否则默认不强加繁琐的 Git 流程；简单改动轻量提交，团队协作规范治理。**

## 1. 适用条件与分支分级

版本控制的价值在于让代码改动**可追溯、可回滚、不污染主干稳定代码**，而不是给每一个随手小修改都套上沉重枷锁。

> [!IMPORTANT]
> **仅当用户明确提出版本控制诉求时才启用本模块**（例如：指定了分支名称、要求使用 Conventional Commits 规范、要求提 PR 或遵循主干保护规则）。
> 哪怕仓库本身是团队多人协作或存在 `main` 主干，只要用户没有显式要求，一律跳过本模块并在开发思路中简述跳过理由（如“用户未指定 Git 策略，按普通提交处理”）。

当用户明确提出要求时，根据实际协作形态选择最合适的级别：

| 级别 | 适用场景 | 建议做法 | 输出内容 |
| --- | --- | --- | --- |
| **L0 直接提交** | 单人开发、本地实验性改动、无共享主干污染风险 | **不额外建分支**，直接在当前分支开发提交；遵守规范提交格式 | 简述跳过建分支理由 + 提交信息规范 |
| **L1 短特性分支** | 多人协作或有共享主干，本次改动为一个独立完整的功能或修复 | 从主干开辟简短的特性分支（如 `feat/xxx`），完成后合并回主干 | 分支命名 + 目标分支 + 提交规范 |
| **L2 受保护主干** | 仓库设置了受保护分支（Protected Branch），强制代码评审（Code Review）或 CI 检查 | 建立特性分支 + 提交 PR / MR + 自动化测试全绿后合入 | L1 内容 + PR 评审流程 + 合并策略 |

## 2. 常见分支模型选择

优先顺应当前项目已有的分支管理规范。如果项目没有明确规定，参考以下三种常见形态：

| 分支模型 | 适用场景 | 分支结构 | 特点与建议 |
| --- | --- | --- | --- |
| **直接主干开发** (Trunk-based) | 单人个人项目、本地小实验、极小改动 | 仅使用当前主干（如 `main`） | 最轻量，无分支切换成本；要求改动小、风险低 |
| **短特性分支** (GitHub Flow) | 持续集成、敏捷迭代、主流开源项目与绝大多数团队 | `main`（主干） + `feat/*` / `fix/*`（特性分支） | **最推荐的现代实践**。分支生命周期短（1~2 天），合完即删，配合自动化 CI 门禁 |
| **经典 Git Flow** | 周期性发版（如 App 客户端）、需要长期并行维护多个历史大版本的传统产品 | `main`（生产） + `develop`（开发） + `feature/*` + `release/*` + `hotfix/*` | 流程较重，分支多；对于互联网 Web/SaaS 持续交付项目通常过重，慎用 |

### 分支命名建议
- 功能开发：`feat/功能简述`（如 `feat/batch-approve`）
- 缺陷修复：`fix/缺陷简述`（如 `fix/coupon-threshold`）
- 文档更新：`docs/说明`（如 `docs/update-readme`）
- 重构优化：`refactor/重构模块`（如 `refactor/order-service`）

## 3. 提交信息规范（Conventional Commits）

提交记录（Git Commit）是代码演进的履历。良好的提交信息应当做到：**意图单一、原因清晰、便于回滚**。

统一遵循业界与 Google 广泛推荐的规范格式：

```text
<type>(<scope>): <subject>

[可选的详细正文 body，解释为什么这么做]

[可选的页脚 footer，如关联的 Issue: Fixes #123]
```

### 常用提交类型（Type）
- **feat**: 新增业务功能
- **fix**: 修复 Bug
- **docs**: 仅修改文档或注释
- **style**: 不影响代码逻辑的格式调整（空格、分号、格式化）
- **refactor**: 代码重构（既不加新功能，也不修 Bug）
- **test**: 新增或修改测试用例
- **chore**: 构建工具、依赖包更新或辅助配置修改
- **perf**: 提升性能的代码优化

### 提交原则
1. **单一职责**：一个 Commit 只做一件事。严禁把“修了 Bug A”和“重构了模块 B”混在同一个 Commit 里提交；
2. **描述准确生动**：
   - ✅ `fix(coupon): 满减券门槛由严格大于改为大于等于包含临界值`
   - ❌ `update` / `fix bug` / `wip` / `修改了一些问题`
3. **解释 Why（为什么）**：对于较复杂的改动，在 Commit 正文里解释修改的原因和业务考量；
4. **禁止滥用 `--no-verify`**：严禁随意绕过项目的预提交检查（pre-commit hook）。

## 4. 代码合并与主干保护

### 4.1 合并方式选择

- **Squash and Merge（压缩合并）**：
  把特性分支上的多个琐碎提交压成一个整洁的提交合入主干。**日常最推荐**，能让主干的 Git Log 保持干净清晰。
- **Merge Commit（普通合并提交 `no-ff`）**：
  生成一个专门的合并提交节点，保留特性分支上的所有原始提交历史。适合需要完整追踪分支过程的大型特性。
- **Rebase and Merge（变基合并）**：
  把提交线性变基到主干后合入，历史完全线性，但如果提交过多容易产生复杂的冲突处理。

### 4.2 受保护分支（L2）安全守则

当仓库设置了主干保护时，严格遵守以下红线：
1. **主干禁止直接 Push**：所有代码变更必须通过特性分支提 PR / MR 进入；
2. **CI 自动化门禁必须全绿**：合并前确保所有自动化测试与代码检查全部通过，严禁带病合并；
3. **代码评审（Code Review）**：重大或敏感逻辑改动，需经过至少一名同伴或技术负责人审查；
4. **紧急修复（Hotfix）同样需要防线**：即使在线修复 Bug，修完后也必须将代码合回主干并补齐自动化回归测试，绝不能借“紧急上线”为借口留下未受控的隐患。

## 5. 自查清单与避坑指南

### 5.1 自查清单（提交前核对）
- [ ] 仅在用户明确提出 Git 策略时启用了本模块，未向普通小任务强加流程；
- [ ] 分支命名清晰，符合仓库约定；
- [ ] 提交信息符合 Conventional Commits 规范，表达了明确的业务意图，没有 `wip`/`update` 等无意义词汇；
- [ ] 每个 Commit 职责单一，没有把不相干的代码混在一起；
- [ ] 受保护主干的 PR 评审与 CI 自动化测试已确认通过，未私自强推。

### 5.2 常见踩坑反例

| 常见反例 | 危害 | 正确做法 |
| --- | --- | --- |
| **单人写个小脚本也要搞复杂的 Git Flow** | 流程繁琐，徒增认知与操作成本 | 单人或小改动直接在当前分支开发，保持规范提交即可 |
| **直接往团队共享主干强推代码** | 破坏主干稳定性，极易覆盖他人代码 | 走特性分支 + PR 合并 |
| **提交信息写 `fix` / `update` / `111`** | 换人接手或日后排查问题时，完全不知道当时改了什么 | 清楚写明改动类型、影响模块与核心原因 |
| **一个 Commit 提交了几千行五花八门的代码** | 出问题时无法单独回滚某一个特定功能 | 拆解为多个逻辑清晰、可独立回滚的小 Commit |
| **用 `--no-verify` 强行跳过检查** | 把代码格式错误或挂掉的测试带入仓库 | 排查并修复挂掉的检查项，严禁绕过门禁 |
| **项目已有约定，偏要自搞一套分支规则** | 破坏团队既有协作习惯，造成混乱 | 优先顺应当前项目既有的分支和提交命名约定 |
