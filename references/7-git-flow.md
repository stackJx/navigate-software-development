# Git Flow 模块

本模块用于把版本控制策略纳入开发前合同,使命中任务在变更前明确分支、提交、合并与保护策略,而不是事后补提、直接堆在主干或绕过保护规则。先按任务性质选择投入档位,再决定是否采用某种分支模型;目录、分支名和工具都不是设计起点。

## 1. 适用性与投入门禁

Git Flow 门禁的价值是让变更可追溯、可回滚、不污染共享主干,不是给每个小改动强加流程。**本模块只在用户显式声明要用版本控制流程时进入**——点名 Git Flow / 分支模型 / 提交规范 / PR / 评审 / 合并与主干保护,或要求把变更合入受保护分支;仓库多人协作或存在共享主干本身不触发,完整判定见主路由「Git Flow 选择门禁」。进入后先判断投入档位,**只做该档要求的最小交付物**,不为完整而铺满:

| 档位 | 观察到的事实 | 建议投入 | 最小交付物 |
| --- | --- | --- | --- |
| **L0 直接提交** | 单人仓库、无共享主干、或仅本地实验性改动 | 不建分支,直接在当前分支提交;但仍遵守提交规范 | 一句跳过理由 + 提交粒度约定 |
| **L1 短分支** | 多人协作或有共享主干,本次为独立可合并的纵向切片 | 从主干开短特性分支,完成后合并回主干 | 分支命名、合并目标、提交规范 |
| **L2 受保护主干** | 仓库有保护分支、强制评审或 CI 门禁 | 短分支 + PR/评审 + CI 通过后合并,遵循保护规则 | L1 + 合并方式、保护规则、CI 验证 |

档位由**协作形态与共享主干风险**决定,不由仓库规模决定:一个大仓库里的一次个人实验可能是 L0,一个小团队仓库的一次生产功能修复通常是 L1 或 L2。命中高档不意味着要补齐低档的全部产物,只需覆盖本档列出的最小集。

不要因为仓库多人协作、存在共享主干或有多分支就自动进入本模块——用户未显式声明一律跳过并写一句理由。纯分析、纯方案、只读调查和不应触发的问答同样不进入本模块;微变更命中快速通道时按其规则压缩篇幅,但不跳过门禁。

新建分支前先检查:

- 这是独立的可合并切片,还是和其它在途变更强耦合?
- 当前仓库已有约定的分支模型与保护规则吗?优先复用,不另起一套。
- 变更会触及共享主干或他人正在使用的分支吗?

## 2. 分支模型选择

优先复用仓库既有约定。无约定或约定不明时,按团队规模与发布节奏选择,**允许结论是"不使用分支模型、直接在主干提交"**。三种主流模型并列,不预设谁更优:

| 模型 | 适用观察 | 关键分支 | 主要代价/检查 |
| --- | --- | --- | --- |
| **直接主干** (trunk-based / no-branch) | 单人或实验性改动,无共享主干风险 | 仅当前分支 | 改动可一眼核验、可回滚;不适合多人并发改同一区域 |
| **GitHub Flow** | 持续部署、短周期发布、多人协作 | `main` + 短特性分支 | 分支生命周期短,合并后即删;需主干保护与 CI |
| **git-flow** | 有明确发布版本、需维护多个线上版本 | `main` + `develop` + `feature`/`release`/`hotfix` | 流程重,适合版本化产品;小团队或持续部署项目通常过重 |

选择时追问:

- 团队是否需要并行维护多个线上版本?是 → 倾向 git-flow;否 → 倾向 GitHub Flow 或直接主干。
- 是否有持续部署管线?是 → 短分支 + 自动合并更合适;否 → 按发布节奏决定。
- 本次改动是否独立可合并?是 → 独立特性分支;否 → 先拆分或并入相关分支,不为流程强行建分支。

分支命名遵循仓库既有约定;无约定时使用能表达意图的名称(如 `feat/`、`fix/`、`docs/` 前缀 + 简短描述),不使用无意义的序号或人名。命名前缀只是提示,不作为门禁合规证明——正如 DDD 中目录后缀不等于合规。

## 3. 提交规范

提交是变更的可追溯单位。规范目标:每个提交单一意图、信息可追溯、粒度可回滚。

推荐 **Conventional Commits** 形态作为默认参考,但**声明可适配项目既有约定**——若仓库已有提交规范,优先遵循,不另起一套:

```text
<type>(<scope>): <subject>

<body 可选,说明为什么>
<footer 可选,如 BREAKING CHANGE 或关联 issue>
```

常用 `type`:`feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`perf`、`build`、`ci`。这些只是参考词,目标项目若用其他约定(如纯描述式、Jira 前缀、emoji 前缀)则跟随。

提交粒度规则:

- 一个提交表达一个意图,不把无关变更混在同一提交;
- 不为"提交干净"把逻辑相关的变更拆成无法独立理解的碎片;
- 自动生成的改动(如锁文件、构建产物)与对应意图同提交,不单独成提;
- 历史可追溯优先于线性美观——不强求 rebase 压扁,除非仓库约定如此。

禁止:

- `update`、`fix bug`、`wip`、`final` 等无意图信息;
- 一个提交塞入多个不相关用例;
- 用 `--no-verify` 绕过提交钩子(见 §4)。

## 4. 合并与保护

### 4.1 合并方式

| 方式 | 适用 | 注意 |
| --- | --- | --- |
| **Fast-forward** | 短分支、主干无新提交 | 丢失分支历史,不适合需保留特性上下文的场景 |
| **Merge commit** (no-ff) | 需保留特性分支边界 | 产生合并提交,明确标记一次特性并入 |
| **Squash merge** | 一个特性压缩成单一提交 | 丢失细粒度历史,适合小特性;大特性会丢失回滚粒度 |

按仓库约定选择;无约定时,需保留特性边界的用 merge commit,小特性可 squash。不强求统一。

### 4.2 主干保护

L2 档位必须确认主干保护规则,不绕过:

- 共享主干禁止直接推送,变更经分支 + 合并进入;
- 需要评审的仓库,合并前有至少一人评审或明确自评说明;
- CI/测试门禁通过后才允许合并——本地 Git Hook 只能提醒,CI 才是不可绕过的团队门禁(对齐 [4-tdd.md](4-tdd.md) §10);
- 紧急修复(hotfix)走与正常特性不同的最短路径,但仍回到主干并补回归保护,不借紧急之名绕过保护规则。

### 4.3 与其他模块的衔接

- **TDD 命中时**:CI 门禁即测试门禁,合并前测试须绿;提交粒度可对齐红—绿—重构的步骤,但不强制每个 RED/GREEN 各一提交。
- **委派命中时**:多个子代理若会改同一分支,用 worktree 隔离或串行,避免并行争用同一分支/契约(对齐 [6-delegation.md](6-delegation.md) §4)。
- **微变更快速通道**:Git Flow 同样可压缩为各一到两行,但仍须在变更前输出分支/提交策略,不跳过门禁。

## 5. 门禁、产物与反例

### 5.1 交付门禁

本节只列 Git Flow 的**专有**门禁;跨模块通用项(范围可验证、事实与未知项分开、阻塞决策已提出、追踪完整等)见主路由的「开发前合同自检表」,此处不重复。

按 [§1 投入分档](#1-适用性与投入门禁)只核对本档实际产出的项,未做的档位不算未通过。完成前检查:

- 分支模型选择有协作形态或共享主干风险证据,或显式写明"直接主干提交"及理由;
- 仓库已有约定时优先复用,未另起一套冲突约定;
- 提交规范明确,粒度规则可追溯,无 `wip`/`update` 类无意图信息;
- L2 档位下主干保护规则已确认,未被绕过;
- 阻塞性未知(团队分支约定未知、主干保护策略未知)已显式提给用户,未擅自拍板;
- 分支/提交策略可追踪到开发切片与验收标准。

### 5.2 产物

命中时在 `## 开发思路` 中纳入(按档位缩放,简单任务可一到两行):

1. 分支模型与本次分支落位(或"直接主干提交"及理由);
2. 提交规范与粒度约定;
3. 合并目标与方式(L1/L2);
4. 保护规则与 CI 验证(L2);
5. 与 TDD/委派/微变更的衔接说明(命中相应门禁时)。

未命中时用一句话写明跳过理由,不留空标题、不伪造产物。

### 5.3 常见反例及修正

| 反例 | 问题 | 修正 |
| --- | --- | --- |
| 每个改动都建 feature 分支 | 单人/实验性改动被流程拖慢 | L0 直接提交,写一句理由 |
| 直接往共享主干堆提交 | 绕过保护、不可回滚 | L1/L2 走分支 + 合并 |
| `wip`/`fix`/`update` 提交信息 | 历史不可追溯 | 单一意图 + Conventional Commits 或既有约定 |
| 一个提交塞多个用例 | 回滚粒度丢失 | 按意图拆分,不强求线性美观 |
| 用 `--no-verify` 绕过钩子 | 团队门禁失效 | 钩子只提醒,CI 是不可绕过门禁 |
| 紧急修复不回主干、不补测试 | 借紧急绕过保护与回归 | hotfix 回主干并补回归保护 |
| 套完整 git-flow 到持续部署项目 | 流程重于收益 | 按发布节奏选 GitHub Flow 或直接主干 |
| 分支命名当合规证明 | 形式合规掩盖流程缺失 | 复用既有约定,前缀只是提示 |
| 仓库已有约定却另起一套 | 双套规范冲突 | 优先复用既有约定 |

Git Flow 交付的最终标准不是分支图是否齐全,而是变更可追溯、可回滚、共享主干不被绕过,且策略可追踪到开发切片与验收标准。
