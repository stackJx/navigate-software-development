# SDD 规格与任务追踪

SDD（Spec-Driven Development，规格驱动开发）在本 Skill 中用于记录当前需求期望、组织具体实施和核对最终验收。默认以三项方案向用户呈现，遵守 [方案输出协议](../SKILL.md#方案输出协议本-skill-内部优先)，包括用户明确覆盖时的处理；本文的方案前置与三标题要求均以该协议为准。本文集中定义何时将规格保存到文件、如何追踪进度、处理需求变更以及接续未完任务，不另设一套必走阶段或额外工具链。

## 1. 选择规格保存形式与授权范围

先查阅当前用户请求和项目已有约定，再选择最轻量的保存方式：

| 场景 | 处理方式 |
| --- | --- |
| 小改动、一次会话可完成的明确修复 | 对话中的三项方案即可，不强建规格文件 |
| 已有覆盖本次功能的规格或需求文档 | 优先沿用并定位相关章节；先核对当前用户要求和实际代码行为，不再建一份重复规格 |
| 跨会话推进、多阶段交付、复杂接口或状态约束、需要交接 | 在授权范围内保存为文件，并在开发思路中说明文档位置和用途 |
| 用户明确要求保存或更新规格 | 无论任务大小，按用户指定的位置及范围完成文档编写 |

没有既有约定或合适文件时，默认使用 `docs/specs/<feature>.md`。一份文件包含三项方案与任务记录即可；内容规模、所有权或项目规范确有需要时再拆分，不固定生成 `spec.md`、`plan.md`、`tasks.md` 三件套。已有相关规格即使位于其他目录，也优先原地维护，保留无关内容。

**选择保存形式不代表获得额外授权：**

- 仅咨询分析或方案时，向用户输出三项后停止，默认零文件写入；不能为了“遵循 SDD”而自动新建文件保存。
- 明确要求保存规格但暂不实现时，先输出三项方案，再只新建或更新获授权的文档并检查内容；不运行测试、不修改代码与配置、不新建分支或提交。写完规格只表示文档交付完成，不能据此宣称功能已实现或已验证。
- 已授权实现时，在向用户输出三项方案后，按需先保存或更新规格文档；仅在本任务需要运行测试且用户未禁止时，先运行现有测试建立基准，再实施。极简静态改动可只核对内容与 diff；没有现有可运行入口时，如实记录基准未验证。只读调研和对话方案不必等待文件保存；在已获实施授权后，也不默认增加逐阶段审批。
- 用户要求先审批，或存在阻塞性未知项时，遵循主协议等待答复；已获得的授权不重复索取。纯文档任务未授权的代码实现，不能通过规格内容反向推定获得许可。
- 记录规格文档不改变默认模式或协调模式，不自动选用 DDD、TDD 或 Git Flow，也不代表获得了 Git 提交、推送或发布的授权。

## 2. 最小可接续规格

保存到文件的规格文档中保留以下信息，顺应项目已有格式，不为了凑字段而做无谓的重复描述：

1. **标识与修订**：当前功能/工作项标识、修订版本号（如 `r1`）和当前状态；修订版本号不依赖 Git 提交。
2. **需求与依据**：目标、做与不做的范围、角色场景、必要约束；分别注明事实来源、假设和待确认问题，不能把未决问题写成已确认规则。
3. **当前验收条件**：稳定编号 `AC-1` 等（AC，即 Acceptance Criteria 验收条件），描述可观察结果及适用的异常、边界与禁止副作用。顺序改变时不重编编号，撤销项标明原因，不把旧编号分配给无关条件。
4. **任务与验收条件关联**：`T-1` 等任务编号、关联 AC、涉及文件/模块、依赖与归属、验证方法。允许多对多对应，避免为了形式上的对应拆出无意义的细碎任务。
5. **执行记录**：每项任务的状态、涉及文件与修改、验证命令或操作、实际结果与已知限制；如实保留未完成项与具体阻碍。证据应能定位到文件、日志、接口或页面结果，并说明所验证的修订版本和代码状态。

状态可采用“待实施 / 进行中 / 待验证 / 已验证 / 阻塞 / 已撤销”，沿用项目已有名称也可以。状态标签或复选框勾选只表达当前进度；只有实际文件与修改（含代码、配置、测试与文档）符合当前 AC 且具备有效验证证据时，才算真正完成。应执行的测试未执行、环境报错、仅部分通过或仅凭子代理口头自述，都不能标记为已验证；不需要运行测试的静态改动，可用内容与 diff 核对结果作为证据。

下面以“用户明确要求保存优惠券规格”为例展示一份文件的形态。金额、路径和命令需按真实项目调整；文档中的待执行计划不表示获准实施。

```markdown
# 满减券门槛修复

工作项：coupon-threshold · 修订：r1 · 状态：待实施

## 需求分析
- 目标：订单金额等于 100 元时可使用满 100 减 20 券。
- 范围：只调整门槛判断和对应回归测试，保持其他券规则。
- 依据：用户指定的活动规则；代码现状与路径需经只读核对填写。
- 假设与待确认：币种、金额精度和其他券叠加规则沿用已核实的项目约定；未核实项明确列出。

## 开发思路
- T-1：有可运行入口时记录现有测试基准，补临界值回归测试；关联 AC-1、AC-2。
- T-2：调整门槛判断并验证；依赖 T-1，关联 AC-1、AC-2。
- 文件与归属：在核对项目后填写实际文件及各任务负责人。
- 采用 TDD；规则归属明确，跳过 DDD；未要求 Git 策略，跳过 Git Flow。

## 验收标准
- AC-1：符合其他使用条件时，99.99 元不可用券，100 元及 100.01 元可用券。
- AC-2：优惠金额仍为 20 元，其他已覆盖券规则不发生回归。

## 任务记录
| 任务 | 状态 | 修改与验证证据 | 剩余工作 |
| --- | --- | --- | --- |
| T-1 | 待实施 | 未执行 | 核对并记录现有测试基准（无入口则注明未验证）；补测后记录有效失败结果 |
| T-2 | 待实施 | 未执行 | 实现后记录当前代码状态、验证命令与结果 |

## 修订记录
- r1：形成当前范围和验收条件，尚未实现或验证。
```

模板只是起点；实际派发前应补齐涉及任务的真实路径、文件归属、依赖、验证方式和阻塞性决策。不能带着“待填写”的关键上下文让实现代理自行推断。

## 3. 从规格推进实施与验收

1. **确定当前规格与要求**：结合最新用户要求、相关规格文档及只读调研形成三项方案。旧规格描述原先的期望，代码、实际文件和运行表现反映当前行为；二者不符时先指出差异，不能把既有代码的错误行为直接当成正确需求。
2. **按授权记录**：新的写入遵守方案输出协议。需要保存规格文档时，在按协议处理且获授权后再写入当前规格及待实施任务；小任务不强建规格文件。仅要求保存规格的任务，在完成文档编写后即可停止。
3. **按任务实施**：本任务需要运行测试且用户未禁止时，先运行现有测试建立基准，再逐步推进各个可独立验证的任务；无现有可运行入口时记录基准未验证，不编造通过结果。跳过 TDD 不等于免去必要的回归，只要求“不新增测试”仍可按需运行现有测试；极简静态改动可只核对内容与 diff。涉及领域建模时将设计融入开发思路，TDD 模式下将适用的验收条件转化为先失败的测试用例，Git Flow 依然仅在用户明确要求时启用。
4. **按证据更新**：比对实际文件差异（diff，含代码、配置、测试与文档）、测试输出或实际表现后，再更新任务与验收条件（AC）的状态。若当前环境缺少验证条件，如实记录未验证项和后续动作，不能把“已完成修改”等同于“已通过验收”。
5. **完成交付**：逐项对照当前有效的验收条件与实际实现范围，向用户汇报规格文档路径、修订版本、验证证据与遗留未完成项；按项目知识库规范评估是否存在可长期复用的经验与决策。

规格文档随实际业务约定的变化持续维护。方案输出协议生效时，文档内容不能替代主会话在新写入前向用户输出三项方案，仅贴一个文档链接不算已经说明方案；文档内容也不能替代实际的测试与验证证据。

## 4. 需求变化与规格修订

**最新用户要求高于旧规格。** 发现冲突时显式指出来源与影响；能依据用户要求确定的直接修订，关键业务含义仍不明确时提出阻塞项，不自行选一个版本。

- **实质变化**：目标、范围、接口与行为约定或验收条件变化，或原方案走不通时，先暂停受影响的所有写入操作（含代码、配置、测试与文档），按主协议重新向用户输出修订后的三项方案和原因；在授权范围内更新当前规格文档，再继续受影响的实施。仅使用对话方案时同样先在对话中更新三项说明。
- **计划细化**：不改变范围和行为约定的文件定位、步骤顺序或等价实现选择，可以直接更新计划记录，无需引入额外审批。
- **标记影响**：递增修订版本号（如从 `r1` 到 `r2`），简述修改依据和受影响的 AC、任务及证据；不再适用的旧证据标记为失效或待复验，已被替代的旧任务标明去向。保留必要的变更原因，不堆砌逐次操作流水账。
- **同步实施者**：向受影响的代理补发修订说明和摘要，在明确最新规格前，受影响代理必须暂停所有相关写入（含代码、配置、测试与文档）；不受影响且无依赖的任务可继续推进。
- **保持验收诚实**：测试失败应修正实现代码或报告真实限制，不可在收尾时改动 AC、弱化断言以求通过。确因业务要求变化需要调整时，按上述修订流程说明依据，不能掩盖原先的验证结果。

已在规格中明确要求审批的后续动作仍等待审批；修订文档本身不会取消该边界，也不额外要求所有常规细化重新确认。

## 5. 中断恢复与证据适用性

接续未完任务时先进行只读核对，沿用当前任务已有授权与执行模式，不能仅仅因为读到了规格文档就自行推定获得了新任务的实现授权：

1. 阅读最新用户要求、当前规格修订版本、任务记录和阻塞项，确认本次要继续的任务范围。
2. 查看实际 Git 状态/差异（diff）、相关文件和已有验证结果，区分哪些已完成、部分完成、尚未开始，以及是否有其他任务的改动；完整保留用户已有工作。
3. 核对旧证据所验证的代码与文件状态、AC 修订版本、当时执行验证的环境（不仅限于测试环境）和依赖项。出现新修改（含代码、配置、测试与文档）不代表所有证据作废，但必须核对受影响的范围；无法证明依然适用的记录为待复验，不能盲目照搬旧的“已完成”标记。
4. 汇总可复用的修改成果（含代码、配置、测试与文档）、待重新验证的项、剩余任务与依赖关系。新的文件写入前按方案输出协议处理当前方案；若需求发生变化，先按修订流程更新规格文档或对话方案。
5. 只恢复授权范围内的剩余工作。协调模式先确认原代理已停止，再按文件归属恢复原代理或重新派发；无可写代理时报告具体阻碍，不由主会话直接接手实现。

接续摘要应让接手者清楚“按哪一版做、哪些已有证据仍成立、下一步做什么”，而非仅复述进度百分比或任务勾选。

## 6. 子代理交接与文档归属

具体分工遵循 [委派指南](6-delegation.md)。共享的需求与计划文档由主会话统一维护，保持单一写入者；负责实现的子代理向主会话返回实际修改（含代码、配置、测试与文档）、任务/AC 验证结果与修订建议，由主会话复核后统一更新文档状态。若文档本身包含可执行脚本、具体配置或完整实现代码，仍属于实现任务范畴，不能借编写规格之名由主会话越权实现，绕过协调模式的分工约束。

派发消息需包含完整独立的上下文，无需子代理自行猜测：提供当前目标、实现思路与验收条件摘要（方案输出协议生效时已向用户说明）、项目绝对路径、规格文档绝对路径与修订版本（存在时）、本任务及 AC 编号、相关规则约定、允许修改的文件、依赖与文件归属、验证方式和交付格式。没有保存规格文档时也携带上述实际内容；文件路径或编号不能替代实际说明内容。

子代理不得因旧规格或继承会话历史而自行扩大授权范围。发现版本、任务范围、接口或行为约定发生冲突时，立即暂停受影响的所有写入操作（含代码、配置、测试与文档）并回报证据，由主会话统一修订和同步；不允许多个代理并发修改公共规格文档，更不能自行修改验收目标。

## 7. 与知识沉淀的边界

规格文档记录当前任务的需求期望与验证证据；项目知识库则用于留存经过验证、未来仍有价值的业务背景、特殊限制与关键设计决策。改动收尾时按照 [知识沉淀规范](8-knowledge-base.md)提炼核心结论或添加引用，避免把整份规格复制进知识库、避免重复记录任务执行进度，也不要把尚未实际完成的工作写成项目当前事实。对于仅完成文档保存、未实际实施的任务，单单保存规格本身不要求新增知识条目，但也不绝对禁止记录独立有价值且已验证的客观知识。
